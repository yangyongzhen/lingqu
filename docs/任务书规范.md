# 任务书规范（交给 cjh 的那份"说明书"）

> **这份文档回答一个问题**：交给内置 agent（cjh）的那份**任务书**，凭什么算"给全了"？
> 版本：**0.39.112**｜上位文档：[`docs/AI自进化飞轮.md`](AI自进化飞轮.md)（五层结构里"迁移现场"那一层）
> 同族文档：[`docs/经验入库规则.md`](经验入库规则.md)（认知层怎么进）· [`docs/集成cjh.md`](集成cjh.md)（引擎怎么接）
> 相关代码：`src/autoport.cj`（`directiveClauses` / `directiveSectionsOf` / `directiveGapsOf` / `buildAutoPortDirective`）
> 落盘与发送：`src/main.cj:5809` 生成 → `:5813` 写 `<工程>/.lingqu/autoport-directive.md` → `:5826` 发短 kickoff
> 判据代码：`src/tests/directive_spec_test.cj`（清单 ↔ 生成物 ↔ 本文档，三处同源）

---

## 0. 一句话

**任务书是 agent 唯一必读的入口**。工具再有本事，任务书没写 ⇒ agent 只能瞎摸，白烧一轮人工介入（计入 A3）。

所以任务书的验收不是"读起来完整"，而是：**§3 的每一条必备小节都在，且每一条都能说出"缺了会怎样"**。

---

## 1. 为什么单独立一份规范

三件事叠在一起，都是实测撞出来的：

| 事故 | 现象 | 教训 |
|---|---|---|
| **0.37.2 长任务书被丢弃** | 4433 字任务书单帧发过去，cjh 回一帧 `history_messages` 后再无动静；同状态 9 字短句完全正常（`frames=5 / delta:2 / done:2`） | **形态错了，内容再全也没用** → 改成"落文件 + 短 kickoff" |
| **0.39.83 签名没给全** | CLI 早就有 `sign --login` / `sign --auto`，任务书只写了 `sign --path .`；agent 摸到"自己开浏览器登录 AGC 网页"这条死路，拿不到本机回调的 `tempToken`、也不注册设备 | **能力在手、说明书没给 = agent 只能瞎摸** |
| **0.39.99 TLS 栈** | 技能 `references/cargo-patches.md` **早就写着**"`reqwest` 要 `default-features = false`"，agent 照样踩 `openssl-sys` | **「写在技能里」≠「agent 读得到」**——技能是按需读的，症状串与那条经验没有字面联系就翻不到 |

三条指向同一个结论：**任务书是唯一每轮必读的东西**，所以它承担"兜底"职责；技能负责细节，规则/指纹负责确定性兜底。分工见 §5。

> 反面参照（做反了的样子）：把任务书写成"建议你先跑 scan，再…"的顾问口吻 —— 模型就会给完建议停下等人，
> 这正是 D-015 / AGENTS §0.1 明令禁止的退化。

---

## 2. 形态：落文件 + 短 kickoff（不是一条长消息）

| 产出物 | 落在哪里 | 约束 | 判据 |
|---|---|---|---|
| **任务书正文** | `<工程>/.lingqu/autoport-directive.md` | agent 的 bash cwd 就是工程根，它有 `read` 工具；对任何单帧长度上限免疫 | `main.cj:5813` |
| **kickoff** | WS 一条消息 | **必须短（<300 字）**，只说"去读哪个文件"，不复述内容 | `buildAutoPortKickoff` + 单测 `testKickoffStaysShortAndPointsAtFile` |
| **路径** | 全文一律**绝对** | agent 的 cwd 是目标工程，相对路径全部失效（§4-70） | `cliPath` 由命令层填绝对路径 |

**为什么 kickoff 不复述内容**：复述就是**第二个漂移源**——改了任务书忘了改 kickoff，agent 读到的两处说法打架。
kickoff 只负责"把门推开"（读这个文件 → 先跑 `resume` → 别问我确认）。

## 3. 必备小节清单（**与 `directiveClauses()` 同一份**）

下表就是代码里那份清单，第一列是**小节标题的稳定前缀**（生成物里必须原样出现）。
「缺了会怎样」一列同时也是"这一条还能不能删"的唯一依据 —— 要删条款，先读它。

| 小节 | 触发条件 | 缺了会怎样 |
|---|---|---|
| `【灵渠 · AI 自动迁移任务书】` | always | 不点明这是任务书，模型会当成随便一段聊天，给完建议就停下 |
| `**你是这次迁移的执行者，不是顾问。**` | always | 0.36.0 就是这么退化的：AI 只出建议，命令还得人点 |
| `## 工具箱` | always | agent 的 bash cwd 是目标工程，相对路径全失效；没有可复制的绝对路径，整条循环就断了（§4-70） |
| `## 原生 UI 能力` | always | 选文件/选目录/分享/开外部应用在 ArkWeb 里没有原生等价物，不写它就自己开浏览器或猜路径（§4-162）；桥的铁律与有没有 `lingqu-cli` 路径无关，所以无条件给 |
| `## 把踩到的坑记下来` | cli | 会话会被压缩，细节一压就淡；不落成笔记就等于没踩过（飞轮第 ① 步的入口） |
| `**判断只认落档**` | always | 退出码 0 不等于通过（§4-63 假绿）；不写这条，它会拿"跑完了"当"迁好了" |
| `## 工作循环` | always | 不给固定循环，它会跳步或反复重跑已通过的步骤，白烧轮次 |
| `## 当前落档` | state | 不给现状就会自己去猜从哪继续，通常等于重跑一遍扫描 |
| `## 本次范围` | half | 半自动不写范围，它会顺手把 build/hap/deploy 全跑了，人失去逐步确认的意义 |
| `## 真机：` | always | 不说清设备在不在线，它会把"未跑"当成"失败"，或者对不存在的设备反复重试 |
| `### 先证「移植做完了」` | device | D-020：A4 分母是移植项，不写清就会去替原作者逐条点业务功能，永远点不完 |
| `### 业务功能冒烟` | device | 不把冒烟单列，业务功能失败会被算进移植通过率（§4-63 第三态） |
| `## 纪律` | always | 平台限制≠失败、未验证≠通过、禁全盘搜索——不写就会谎报或挂死（2026-11-07 事故） |
| `## 插件不满足：三层适配优先于降级` | always | 外部反馈（2026-11-20）：轻易降级就丢原软件功能特性；不写清适配路径，agent 撞到无对应物的插件只会降级 |
| `## 鸿蒙知识库（MCP 工具）` | always | 0.39.130：cjh 已接入华为开发者知识库（searchDocuments/getDocumentsById），但任务书不写"何时该查"，agent 会靠模型记忆猜 API 语义——猜错就白烧一轮编译 |
| `## 交叉编译的硬前置` | always | 缺 `.cargo/config.toml` 的 `[env]` 段时 cc-rs 必然失败，不说清它会去改 Rust 源码 |
| `## TLS 栈` | always | `reqwest` 默认特性拉进 `openssl-sys`，OHOS 上必死；技能里写了也没用，症状串对不上（§4-150） |
| `## 装配 HAP 前：鸿蒙脚手架必须先生成` | always | 不写 `cargo tauri ohos init --ci`，它到 hap 这一步只会撞墙，或去全盘搜 `gen/ohos` |
| `## 签名与登录` | always | CLI 早就有 `--login`/`--auto`，任务书没写 ⇒ agent 自己开浏览器登录，白花一次人工介入（§4-130） |
| `## 预算与收尾` | always | 不给预算它会无限挂着；不给收尾格式，人就只能读一大段散文 |

### 3.1 四个触发条件

| 条件 | 常量 | 什么时候成立 |
|---|---|---|
| `always` | `DIRECTIVE_WHEN_ALWAYS` | 永远（不需要传） |
| `cli` | `DIRECTIVE_WHEN_CLI` | 命令层拿到了 `lingqu-cli` 的**绝对路径**（`cliPath.size > 0`） |
| `device` | `DIRECTIVE_WHEN_DEVICE` | 真机在线（`inp.device`），决定要不要跑 deploy/verify/probe |
| `state` | `DIRECTIVE_WHEN_STATE` | 有落档摘要（`stateLines.size > 0`） |
| `half` | `DIRECTIVE_WHEN_HALF` | 半自动作用域（`scope` 不是 `all`/空） |

### 3.2 四种常见变体该有哪些

| 变体 | 传的 `whens` | 例 |
|---|---|---|
| 全流程 + CLI + 真机在线 + 有落档 | `[cli, device, state]` | 界面「🤖 开始 AI 自动迁移」的典型现场 |
| 全流程但没拿到 CLI 路径 | `[device]` | 工具箱整段退化成"命令名举例"，agent 要自己找 `lingqu-cli` |
| 全流程但设备不在线 | `[cli, state]` | deploy/verify/probe 一律跳过，落档写"未跑" |
| 半自动（如只做签名） | `[cli, half]` | 左侧各屏的「🤖 交给 AI」，做完就停 |

判据代码：

```
directiveSectionsOf(whens)              → 这一份变体该有的小节（Array<String>）
directiveGapsOf(生成物, 该有的小节)      → 缺了哪些（空 ArrayList 才算"给全了"）
```

**空 body 一律判"全缺"**：读不到 ≠ 都齐了（§4-136 假绿的教训）。

## 4. 全自动 vs 半自动

| | 全自动 | 半自动 |
|---|---|---|
| `scope` | `all` 或空 | `port` / `deps` / `build` / `hap` / `sign` / `deploy` / `verify` |
| 标题 | `（全流程）` | `（半自动：只做「<中文标题>」这一步）` |
| 收尾条件 | 一路干到 `verify` 落档，或用完预算 | **做完就停**，下一步由人点（`autoPortScopeGoal`） |
| 铁律 | 别替原作者点业务功能（D-020） | **别顺手把后面的步骤也做了** |

为什么半自动必须"做完就停"：否则"只让它改改造"会变成它顺手把 build/hap/deploy 都跑了，
人反而失去了"逐步确认"的意义（这是界面各屏「🤖 交给 AI」的存在理由）。

中文标题由 `autoPortScopeTitle` 统一给出（界面按钮、任务书标题共用一份，别各写各的）。

## 5. 三层分工：任务书 / 技能 / 规则与指纹

| 写哪儿 | 适合什么 | 什么时候改 |
|---|---|---|
| **任务书**（`src/autoport.cj`） | 每轮必读、agent 绕不过去；**确定性兜底**与**硬顺序**（例："脚手架生成之后必须重跑 `port --apply`"） | 发现"工具已经有、它却不知道"就写这里 |
| **技能 references**（`skills/t2h-ohos-port/`） | 按需读、细节多：桥骨架、签名材料矩阵、工具链版本 | 细节长篇，任务书里只留一句"先读它再动手" |
| **规则 / 指纹**（`src/port/`） | 可枚举的确定性改造（`R2-PORT-0xx`）、唯一可识别的报错串（`FP-0xx`） | 能确定性解决时——重跑命令就好，不用靠模型读文档 |

两条判据：

1. **能确定性解决的进规则，别指望"读到就会用"**（§4-150）。技能管"人能查"，兜底要进 agent 绕不过去的规则/指纹/任务书。
2. **只有唯一可识别的报错串才进指纹表**（§4-164：全数字且 ≥7 位）。非数字 marker 不唯一，硬钉进判据反而会污染匹配顺序。

## 6. 纪律红线（任务书里写死的六条，及理由）

| 红线 | 为什么 |
|---|---|
| **平台限制 ≠ 失败** | 鸿蒙没有的能力登记为限制，不算 bug，更不许写"已修复" |
| **未验证 ≠ 通过** | 没证据的项写 `unknown`（§4-63 第三态） |
| **禁止全盘搜索** | 2026-11-07 事故：`find / -maxdepth 6 …` 把工具调用挂死 565s+，孤儿 `find` 累计 CPU 605s。脚手架只有两处（`<工程>/gen/ohos`、`<工程>/src-tauri/gen/ohos`），没有就如实报缺 |
| **中文一律走 `--body <文件>`** | 仓颉程序在 Windows 上接不了非 ASCII 的 argv（`Invalid unicode scalar value`，§4-119） |
| **不许伪造签名、不许改包名蹭 profile** | 宁可如实报"签名未完成、等人登录"，也不要交一个装不上的 HAP 说成迁完了 |
| **要人做事就一次性说清** | 用 `lingqu-decision` 块写"为什么必须 / 点哪里 / 关键值（如本机 UDID）"，说完停下等人，别绕圈 |

## 7. 新增能力时：三个落点（缺一个就是缺口）

1. **任务书对应小节**：写清"哪一步之前必须有它"，以及判据（看哪个落档字段）。
2. **技能 references 一节**：细节长文放这，任务书里给一句指路（"先读 `references/xxx.md` 再动手"）。
3. **规则 / 指纹兜底**：可枚举的改造进 `R2-PORT-0xx`；唯一报错串进 `FP-0xx`，并保证 references 里查得到
   （`fingerprintDocGapsOf` 是判据，见 0.39.111）。

### 7.1 反例清单（看到就说明做反了）

- 任务书里出现「**建议你**执行……」「你可以先……」然后没有下一步动作；
- 同一条能力**只写在半自动那一支**，全流程里没有（§4-130 第二条：只点这一步的人反而知道得更少）；
- 写「某报错是正常的」却**没写同号不同成因的那一种**（agent 会拿它当挡箭牌放过真问题）；
- 新增能力只写了技能 references，**没进任务书**（agent 大概率读不到）；
- 任务书里给了**相对路径**（agent 的 cwd 是目标工程，§4-70）；
- kickoff 里复述了任务书内容（两处漂移源）。

## 8. 怎么验收「任务书给全了」

| 层 | 判据 | 在哪 |
|---|---|---|
| **清单 ↔ 生成物** | 四种变体的生成物，`directiveGapsOf` 必须为空；截断一份必须报出缺哪几条 | `src/tests/directive_spec_test.cj` |
| **本文档 ↔ 清单** | §3 表格必须**逐字**列出 `directiveClauses()` 里每个小节名（读真实文档断言，读不到直接红） | 同上 |
| **清单无重名且理由齐全** | `directiveClauses()` 的小节名不重复，`why` 都不为空（删条款的人要能读懂它防的是什么） | 同上 |
| **行为** | 换一个带原生 UI 的工程重跑 `autoport`，看它是否按 §3 对应那节动手 | `t2h:autoport_start` |

**诚实的边界**：前三条只保证"**小节在**"，**不保证 agent 照做**。
"写了任务书" ≠ "它读了" ≠ "它照做了" —— 行为验收只能靠真实迁移跑一轮，结论写进 `docs/进度记录.md`（AGENTS §1 第 5 条）。

## 9. 变更流程

| 你要做的事 | 必须同步改的地方 |
|---|---|
| 改小节**文案** | `directiveClauses()` 的 `section` 前缀 + 本文档 §3 表格（单测会红，跑一次就知道漏哪） |
| **新增**小节 | ① 先定触发条件 ② 写进 `directiveClauses()` ③ 写进本文档 §3 ④ 补单测变体 |
| **删**小节 | 先读 `DirectiveClause.why`；说不出"这条的前提已经不成立"就别删 |
| 改预算/停滞阈值 | `AUTOPORT_MAX_ITERATIONS` / `AUTOPORT_MAX_MINUTES` / `AUTOPORT_STALL_POLLS` / `AUTOPORT_BUSY_MAX_SECS` + `docs/设计决策记录.md` |

版本号与 `CHANGELOG.md` 同步规则见 AGENTS §5 / §6。
