# Tauri→鸿蒙 PC 迁移工具 · 产品化方案（GUI 版 v1）

> **课题**：课题 8「AI 驱动的 Tauri 应用迁移到鸿蒙 PC 的工具」（研发效能与自动化工具）
> **交付截止**：2027-03-03　**本方案日期**：2026-10-28
> **产品代号**：**灵渠 / `Lingqu`**（工作台名：**灵渠迁移台**）
> **一句话**：用**仓颉**写一个**自己就长在 cj-tauri 上的桌面工作台**，把 `cjh` 当内嵌 AI 引擎，
> 把上一个五个月里"翻几千字踩坑笔记手工迁移"的过程，做成**开箱即用、看得见、可断点、有证据**的一条流水线。

---

## 1. 结论先行：产品形态定什么

### 1.1 形态

**一个桌面 GUI 工作台（cj-tauri 应用）**，不是又一个 CLI 脚本。

| 层 | 选型 | 作用 |
|---|---|---|
| 外壳 / UI | **cj-tauri**（仓颉 + 系统 WebView，鸿蒙走 ArkWeb） | 窗口、多标签、菜单、IPC、资源与配置、打包分发 |
| AI 引擎 | **cjh**（仓颉 Coding Agent Harness，已有 web 模式） | 规划/诊断/改码/解释，工具调用与审批流 |
| 迁移引擎 | **仓颉主导 + 外部工具编排**（cargo / ohrs / hvigor / ohpm / hdc） | 扫描、规则改造、构建、部署、取证 |
| 知识资产 | 规则库 + 报错指纹库 + 5 个真实迁移样本 | 让 AI 不靠"猜" |

### 1.2 为什么是 GUI，而不是 CLI

不是因为"GUI 好看"，而是这个任务的三个客观属性决定的：

1. **长流程**（20~90 分钟，含交叉编译）：CLI 里人只能"等"，GUI 能"同时看四件事"——日志、依赖矩阵、证据灯、Agent 在干什么。**断点续迁**在 GUI 里是天然的（状态可见），在 CLI 里要人记。
2. **断点决策密集**：单应用≤5 处人工介入（验收线），每处都是"这里要不要降级？"的选择题——GUI 的审批卡 / diff 预览 / 一键对比是最合适的载体。
3. **证据要给人看**：验收标准里"核心功能可用率 ≥80%"必须有**可展示的证据**（截图、日志、探针结果、评分）。报告页本身就是产品的一部分。

### 1.3 一个额外的说服力（顺手拿分）

cj-tauri 已经**在鸿蒙 ArkWeb 真机闭环**（建窗/装载/IPC/多窗口/菜单/剪贴板，2026-10 真机取证，见 `docs/平台能力矩阵.md`）。
所以本工具可以做到：**同一个代码库，编出 Windows 工作台 + 鸿蒙 PC 版工作台**。
答辩时这句话很硬："我们自己就是用这套技术栈把工具跑上鸿蒙 PC 的，这就是 Rust+ArkWeb 混合架构范式的活样板。"

> 但要说实话（方案里必须写清）：**鸿蒙 PC 版是"伴侣端"**——只做项目浏览、报告查看、证据回看、远程审批/日志看板。
> 因为迁移动作本身要求本机有 Rust 工具链 + OHOS SDK + hvigor + hdc，这些在鸿蒙 PC 上不齐备。
> 主战场仍是 Windows/Linux/macOS 桌面工作台。**把它写清楚，比吹"全平台"更可信。**

## 3. 三个关键决策（每个都附"为什么不选另一条"）

### D1：GUI 外壳用 **cj-tauri**，不用 Electron / Tauri / 纯浏览器

| 候选 | 否决理由 |
|---|---|
| Electron | 100MB 起、带 Chromium，与课题"轻量 Rust+系统 WebView"叙事自相矛盾 |
| Tauri 官方 | 能用，但工具要跑在鸿蒙 PC 上就得吃 Tauri 的 OHOS fork，等于把"被迁移对象"的不确定性引入"迁移工具"自身 |
| 纯 Web（起个本地服务 + 浏览器） | 没有原生窗口/文件对话框/多窗口，工作台体验差；且拿不到"工具本身是仓颉应用"这个加分点 |
| **cj-tauri（选用）** | 仓颉原生、几 MB 产物、系统 WebView、已有鸿蒙 ArkWeb 真机闭环；**且与本项目的迁移对象（Tauri 应用）同构**——工具自己就是一个"类 Tauri 应用"，迁移规则在自身上可自测（吃自己的狗粮） |

### D2：AI 引擎用 **cjh（进程外，web 模式）**，不自己写 agent、也不进程内嵌

cjh 已具备我们需要的全部能力（`libs/cjllm` + `src/agent/loop.cj` + 14 个内置工具 + 技能系统 + MCP + 插件 + 审批流 + web/REST/WS 会话管理）。
`cj-tauri/examples/ai-chat/src/cjh_host.cj`（33KB）已经把"拉起 cjh web 子进程 / 健康轮询 / 复用既有实例 / 收尾"这套写好了，**可直接复用**。

| 候选 | 否决理由 |
|---|---|
| 进程内嵌 cjh 为库 | cjh 是 executable 根包（仓颉限制：executable 根包不能被导入）；进程内还会把 agent 的崩溃面耦合进 UI |
| 自己写个 mini-agent | 白白丢掉 cjh 的技能/审批/压缩/工具注册，三个月做不完 |
| **进程外 `cjh web`（选用）** | 复用已验证实现；崩溃隔离；可换 cjh 版本；多会话并发；还能让用户在 cjh 里用同一份会话继续干别的 |

**迁移能力怎么进 cjh**：做成 cjh 的**技能（skills）+ 工具（plugin 或 MCP server）**，而不是塞进 prompt：

```text
~/.cjh/skills/
  t2h-migrate-tauri/SKILL.md      ← 迁移方法论（从你说的 6 篇 + 本地 4 个样本蒸馏）
  t2h-ohos-pitfalls/SKILL.md      ← 踩坑指纹表（现象→根因→修法）
t2h MCP server（或 cjh plugin，本项目提供）
  t2h.scan / t2h.deps / t2h.port / t2h.build / t2h.deploy / t2h.verify / t2h.report
```

这样 GUI 只负责"可视化 + 审批 + 状态机"，agent 能力全部来自 cjh，边界干净。

### D3：迁移引擎用 **仓颉主导 + 外部工具编排**，核心解析不依赖 LLM

- 确定性部分（Cargo.toml/toolchain/config/能力清单/图标/打包参数）→ **仓颉直接算**（`cjcfg`/`cjutil` 已有基础），零 token；
- 语义部分（平台 API 降级、ArkWeb 兼容层注入）→ **规则优先，LLM 兜底**；
- 重活（编译/打包/部署）→ 调外部工具，自己做**结构化解析**（cargo `--message-format=json`、hvigor 日志、hdc 输出）。

**这条是产品可信度的根**：用户看得见"哪一步是规则做的、哪一步是 AI 做的、哪一步是我做的"。

## 4. 系统架构（进程 / 端口 / 生命周期）

```text
┌──────────────────────────── 灵渠工作台（一个进程，cj-tauri）───────────────────────────┐
│  前端 UI（HTML/CSS/JS，ArkWeb / WebView2 通用）                                          │
│    ├─ 左栏：7 步流程状态机       ├─ 中栏：画像/依赖/流水线/证据                         │
│    └─ 右栏：Agent Dock（对话 + 工具卡 + 审批卡）                                        │
│         ↕ `window.__CJ_TAURI__.invoke / listen`（JSON postMessage）                     │
│  仓颉后端                                                                                │
│    ├─ 迁移引擎 t2h_core：Scanner / Rules / Builder / Verifier / Reporter                 │
│    ├─ cjh_host（复用 ai-chat 实现）：拉起/复用/心跳/收尾 cjh 子进程                       │
│    ├─ 进程编排：cargo、ohrs、hvigorw、ohpm、hdc（超时/取消/输出流式回传）                  │
│    └─ 工作区存储：<workspace>/.lingqu/{project.json,tasks.json,evidence/}                │
└───────────────┬─────────────────────────────────────────┬───────────────────────────────┘
                │ HTTP + WS（127.0.0.1:8765，复用优先）      │ 子进程 stdio / 文件
                ▼                                          ▼
        ┌───────────────────┐                    ┌────────────────────────────┐
        │ cjh（agent 引擎）  │                    │ 工具链：rustc/cargo/ohrs   │
        │ /api/health        │                    │ hvigorw / ohpm / hdc       │
        │ /api/sessions      │                    │ OHOS NDK clang             │
        │ /api/tasks         │                    └────────────────────────────┘
        │ /api/skills        │
        │ /api/mcp           │      ┌──────────────────────────────────────┐
        │ /api/workspaces    │─────▶│ t2h MCP server（迁移工具面）          │
        │ WS：流式消息/工具事件/审批 │      │ scan/deps/port/build/deploy/verify  │
        └───────────────────┘      └──────────────────────────────────────┘
```

**关键工程约定**

| 项 | 约定 |
|---|---|
| cjh 端口 | 8765，**复用优先**（已有活实例就复用，不抢用户的）；本工具拉起的才由本工具收尾 |
| 健康探针 | `GET /api/health`，10s 轮询（沿用 ai-chat 口径） |
| 降级 | cjh 不可用 → 工作台进入「手动模式」：规则改造/构建/部署照常，只有 AI 面板显示"引擎未启动"并给一键修复入口 |
| 会话策略 | **一个迁移项目 = 一个 cjh 会话**，会话 id 写进 `project.json`，断点续迁时可恢复上下文 |
| 长任务 | 构建/部署在主进程外跑，输出经 cj-tauri 事件流式回传（不冻 UI） |
| 端口/路径 | 全部可配，落 `~/.lingqu/config.json`；工作区路径走 cj-tauri 的**路径 scope** 白名单 |

## 5. 界面设计（UI 效果图见 `ui-mockup/index.html`）

### 5.1 信息架构

```text
窗口
├── 顶栏：应用图标 · 项目名 · 设备状态（hdc: 2in1 已连接）· 主题 · 帮助
├── 左栏（导航，7 步 + 状态灯）
│     ① 项目  ② 画像  ③ 依赖  ④ 改造  ⑤ 构建  ⑥ 验证  ⑦ 报告
├── 中栏（主工作区，随步骤切换）
└── 右栏（Agent Dock：对话 / 工具卡 / 审批卡 / 上下文用量）
```

### 5.2 七个界面（元素级）

**① 项目 Project —— 入口**
- 拖入文件夹 / 选择目录；最近项目卡片（含上次进度"停在第 4 步"）
- 项目卡要素：名称、Tauri 版本、前端栈、bundleId、上次评分、HAP 产物状态

**② 画像 Profile —— "先算清楚"**
- 顶部：**可迁移度评分环**（78/100）+ 五个维度条（构建链/依赖/运行时/平台 API/分发）
- 中部：五类清单页签 —— **命令 / 事件 / 插件 / 前端资源 / 平台 API**，每行带"处置结论"（改造/降级/不适用/人工）
- 底部：阻塞项卡片列表（severity 色标 + 定位到文件行 + 建议动作 + 预估工时）
- 右上：**分析覆盖率 100%（128/128 项均有结论）** ← 直接对应验收标准

**③ 依赖 Deps —— 兼容性矩阵**
- 表头：crate · 当前版本 · OHOS 状态（✅/⚠️/❌/未知）· 依据 · 替代/改造方案 · 操作
- 左侧筛选（仅不兼容 / 仅需 patch / 全量）
- 右侧详情面板：为什么判它不兼容（源码特征 / 平台 syscall / 已知 issue）+ 建议 diff
- 底部：一键"应用全部建议"（走审批）

**④ 改造 Port —— 执行与断点**
- 左：**步骤时间线**（8 阶段，每步 状态/耗时/结果），当前步高亮，可从任意步"从此处继续"
- 右：**实时日志**（等宽，带过滤：全部/仅错误/仅 Agent 动作）
- 中：**动作流卡片**：`R2-001 依赖切 fork ✔`、`R5-002 confirm 降级 ✔`、`⚠ rfd 需人工确认`（点开看 diff）
- 顶部：进度 + **人工介入计数 3/5**

**⑤ 构建 Build —— 流水线**
- 阶段条：交叉编译 `.so` → 前端一致性校验 → HAP 装配 → 签名 → 安装
- 每阶段可展开日志；失败阶段红标 + "诊断"按钮（直接把证据丢给 cjh）
- 右侧：产物卡（`.so` 大小与 AssetKey 指纹、HAP 大小与版本号、签名类型）

**⑥ 验证 Verify —— 证据**
- 功能清单打勾表（从画像自动生成），每项三态：通过 / 失败 / 未验证
- 证据区：真机截图缩略图、hilog 关键片段、`panic.log`、ArkWeb console 抓取
- 顶部：**核心功能可用率 87%（13/15）** ← 直接对应验收标准

**⑦ 报告 Report —— 交付物**
- 摘要卡：评分、耗时、自动/待确认/人工计数、可用率、风险分级
- 三段式：**做了什么 / 没做什么（含已知限制）/ 需要你做什么（上架清单）**
- 导出：HTML / Markdown / JSON（含证据索引）；"复制给评审看的摘要"

## 6. 迁移引擎（在不重复上一份文档的前提下，只写"产品化必须新增"的部分）

### 6.1 任务状态机（断点续迁的载体）

```text
PENDING → SCANNED → PLANNED → PORTING → BUILDING → VERIFYING → DONE
                                    ↓         ↓          ↓
                                 BLOCKED   FAILED    NEEDS_HUMAN   （都可回到上一步）
```

持久化：`<workspace>/.lingqu/tasks.json`

```jsonc
{
  "schema": "lingqu/task/v1",
  "project": "cc-switch",
  "state": "BUILDING",
  "step": { "index": 5, "name": "build.so", "started_at": "...", "attempt": 2 },
  "counters": { "auto": 9, "assist": 2, "human": 3 },
  "agent_session": "sess_xxx",              // 断点续迁时用它恢复 cjh 上下文
  "artifacts": { "so": { "path": "...", "size": 4718592, "asset_keys": ["ui-9f3a.js"] },
                 "hap": { "path": "...", "version": "1.2.0", "signing": "debug" } },
  "evidence": [ { "id": "E12", "kind": "hilog", "result": "pass", "ref": "evidence/E12.log" } ]
}
```

**为什么这是"产品级"而不是"脚本级"**：改了前端 → 自动判定 `.so` 过期 → 把任务退回 `BUILDING` 而不是假装成功。**这就是验收里"可复制、可规模化"的实体。**

### 6.2 要注入 cjh 的 7 个迁移工具（MCP 或 plugin）

| 工具 | 入参 | 出参（给 agent 看的） | 确定性 |
|---|---|---|---|
| `t2h.scan` | 项目路径 | 画像 JSON（五类清单 + 评分 + 阻塞项） | 全确定 |
| `t2h.deps` | Cargo.toml | 依赖兼容矩阵 + 替代建议 | 规则 + KB |
| `t2h.port` | 规则 id 列表 / 或单个补丁 | 应用结果 + diff + verify 探针结果 | 全确定 |
| `t2h.build` | 阶段（so/hap/all） | 结构化诊断（错误码/指纹/位置） | 全确定 |
| `t2h.deploy` | HAP + 设备 | 安装结果 + 启动结果 + hilog 片段 | 全确定 |
| `t2h.verify` | 功能清单 | 每条证据（截图/日志/探针） | 全确定 |
| `t2h.report` | 任务 id | 报告路径 + 摘要 | 全确定 |

**agent 的职责被压缩到很小很准的一格**：读结构化诊断 → 决定调哪个工具 / 提哪个补丁。它不需要"读一遍整个仓库"。

### 6.3 开源样本候选（验收要 5 个，先定名单）

| # | 候选 | 类型 | 难点（也就是要覆盖的考点） |
|---|---|---|---|
| 1 | `cc-switch`（已有鸿蒙移植实录） | 中型、配置管理 | 原生对话框 / 托盘类能力降级 |
| 2 | `AtomMQTT`（tauri-mqtt-client） | 网络长连接 | stdx socket → 鸿蒙网络栈 |
| 3 | `m3u8dl-tauri` | 媒体/子进程 | 子进程与文件路径沙箱 |
| 4 | Tauri 官方 `examples` 任一（如 file-explorer 类） | 最小可跑 | 构建链 + 资源嵌入的"教科书样本" |
| 5 | `habit-tree`（自有，GPL-3.0，开源可查） | 本地存储型 | localStorage 桥 / `.so` 内嵌前端 |

> 若评审要求"全部为第三方开源"，把 5 换成任一有 Star 的 Tauri 开源应用（候选：`pot-app`、`EcoPaste`、`RustDesk` 的 Tauri 系衍生等），名额在第 1 个月定死。
