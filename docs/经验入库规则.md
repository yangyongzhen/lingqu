# 经验入库规则（notes → 认知层）

> **这份文档回答一个问题**：agent 记下来的"坑"（`<工程>/.lingqu/notes/<工程>.md`），
> **凭什么、按什么格式、写到哪里**，才能变成下一轮**自动吃得上**的东西。
> 版本：**0.39.56**｜上位文档：[`docs/AI自进化飞轮.md`](AI自进化飞轮.md)（五层结构与闸门为什么这么设）
> 同族文档：[`docs/任务书规范.md`](任务书规范.md)（认知层怎么**喂到 agent 面前**——哪些进任务书、哪些进技能、哪些进规则）
> 相关代码：`src/notes.cj`（候选/归档）、`src/port/diagnose.cj`（指纹库）、`src/port/*.cj`（规则库）

---

## 0. 一句话

**机器负责"发现 + 攒证据 + 提议"，人负责"这条能不能进库"。**
本规则给的是**提议的格式**和**裁决的判据**——不是自动化开关。

```
notes 落盘（agent 自述）──suggest──▶ 候选清单 + PR 草稿 ──人复核──▶ 认知层（指纹/规则/技能/§4）
        ▲                                                              │
        └──────────── archive（打 `- 入库：…` 后移出候选池）◀────────────┘
```

---

## 1. 谁能入库：三条件 + 三追问

### 1.1 机械门槛（`notes --action suggest` 按这个筛，可判定、不靠感觉）

| 条件 | 判据 | 代码 |
|---|---|---|
| ① **次数达标** | 同标题出现 **≥ 2 次**（标题归一化：去空白 + ASCII 小写后比对） | `MIN_LESSON_OCCURRENCES` / `candidateLessons` |
| ② **四段齐全** | 现象 / 根因 / 复现 / 修法 **都非空** | `isLessonComplete` |
| ③ **还没入库** | 条目里没有 `- 入库：…` 标记 | `isLessonArchived` |

为什么 ≥2：1 次很可能只是**命令自己写错了**（路径打错、参数顺序错），不是系统的脾性。
为什么四段：技能条目只有"现象 → 根因 → 修法"三段，缺任何一段都写不出来；复现是**验伪**用的。

### 1.2 人的三追问（机械门槛过了也要问，答不上来就不入库）

1. **这是实测还是推测？** ——「修法」必须是你**真的跑通**的那个，不是"应该可以"。
2. **换个样本还成立吗？** —— 至少在一个**别的**工程/版本上复现过一次；只有一个样本就在条目里写明「单样本」。
3. **它属于本项目该管的吗？** —— 第三方工具的 bug（tauri-cli 自己 panic 这种）
   要么进指纹（**识别**它）、要么进 `docs/上游回馈-cjh.md` / 上游仓库（**修**它），
   **不要**写成"我们的修法"塞进技能库冒充经验。

## 2. 写到哪儿：四个去处与选型判据

| 去处 | 适合什么 | 判据（一句话） |
|---|---|---|
| **`skills/t2h-ohos-port/references/pitfalls.md`** | **人工可执行的移植坑**：现象能一句话说清，修法是"改哪里/加什么" | 下次遇到同类错误，agent 读了能**自己动手** |
| **指纹库 `fingerprintLibrary()`（`FP-0xx`）** | 日志里有**稳定子串**（错误码/固定措辞）的错误 | 能做成 marker → 命中即给修法，**不烧模型轮次** |
| **规则库 `R2-PORT-0xx`** | 能**机械执行**的改造（改配置/改代码模式），且能幂等 + 回滚 | 有明确 auto/guide 分档、进 `revertPairs()` |
| **`AGENTS.md` §4** | **本仓自身**的坑（工具链、门禁、脚本、编码规范） | 影响的是"写这个工具的人"，不是"被迁移的应用" |

再补两条常见分界：

- **"该识别"还是"该修"**：目标工程里的错误 → 识别优先（指纹/技能）；
  我们自己代码里的错误 → 修（规则/§4）。
- **"要不要进技能库"**：技能正文会进 **system prompt**，所以只收**通用**的；样本特有的（某个 app 的私有 API）留在
  那个工程的 `notes` 里就够。

## 3. 四段 → 三段的映射（`notes` → `pitfalls.md`）

`pitfalls.md` 的既有条目格式（**不许自创格式**）：

```markdown
### N. <现象的一句话，含报错原文/错误码>
- **根因**：<为什么会这样>
- **修法**：<改哪里 / 加什么 / 见 xxx.md 规则 00N>
```

映射表：

| `notes` 四段 | 落到哪里 | 写法要求 |
|---|---|---|
| **标题** | `### N. …` 的标题 | 把**现象里的可检索线索**提到标题：错误码、报错原文片段（`00308018` / `-lgcc_eh` / `cannot find crate napi_ohos`） |
| **现象** | 一般**并入标题**；需要长描述时加一行 `- **现象**：…` | 不要粘贴整段日志，只留**稳定子串** |
| **根因** | `- **根因**：` | 一句话说清机制；不确定就写"未定位到确切机制（现象与 X 同时出现）"，**不许编** |
| **复现** | **不进正文**，写进"实测出处" | 保留样本名 + 命令 + 落档路径，供人复核 |
| **修法** | `- **修法**：` | 可执行：改哪个文件/加哪段/跑哪条命令；指向 `references/xxx.md` 的规则号 |
| （次数 / 工程 / 时间） | **不进正文**，"实测出处"里写样本与日期 | 例：`实测：juCang（2026-11-01，.lingqu/hap/juCang.json）` |

新条目放在**对应分节**（构建期 / 部署期 / 验证期）的末尾并**续编号**；`pitfalls.md` 头部的
"第 1-4 条 / 5-9 / 10-12"索引也要跟着改——**编号是索引，不是装饰**。

### 3.1 完整示例（真实的一条，可直接照抄结构）

**来源**（`<工程>/.lingqu/notes/juCang.md` 里的一条）：

```markdown
### hvigor 00308018 不是签名问题
- 现象：t2h:hap 报 00308018，日志里是 cargo tauri panic
- 根因：hvigorfile 的 tauri 钩子在非 dev 场景必然失败
- 复现：juCang 工程跑 t2h:hap
- 修法：R2-PORT-015 注掉 .afterRun(buildRustCode)
- 次数：2　工程：juCang　时间：2026-11-01T22:35:52+08:00
```

**入库后**（`pitfalls.md` 的「部署期」或「构建期」新增一条，编号继续往下）：

```markdown
### N. hvigor 报 `00308018 Unknown Error`（日志里是 cargo tauri panic）
- **根因**：`gen/ohos/entry/hvigorfile.ts` 的 `tauriPlugin` 会在构建时执行
  `cargo tauri ohos dev-eco-studio-script`，它需要 dev server 留的 `%TEMP%\<包名>-server-addr`；
  非 dev 场景必然 panic（与签名、源码都无关）。
- **修法**：注掉 `node.getTaskByName('default@ConfigureCmake')!.afterRun(buildRustCode)` 这一行
  （本工具 R2-PORT-015 自动做，带 `hvigorfile.ts.bak` 备份，可回滚）；`lib<模块>.so` 由 `t2h:hap` 自己装配，不需要这条钩子。

> 实测：juCang（2026-11-01，`t2h:hap` 从 `built=false / 0 字节` 变 `built=true / 15,338,218 字节`）。
```

**如果选择做指纹**（更适合"A 里能搜到稳定子串"的）：

```cangjie
lib.add(Fingerprint("FP-021", "dev-eco-studio-script",
    "hvigorfile 的 tauri 钩子在非 dev 场景必失败（tauri-cli 自己 panic）",
    [……修法步骤……]))
```
要点：**marker 取日志里的稳定子串**（不要带行号/路径/字节数），并配一条单测钉住匹配与不匹配两侧。

## 4. 入库之后：回写标记 → 移出候选池

入库完成（PR 合并 / 指纹落库 / 规则进仓）后，在**那一条经验**下面补一行：

```markdown
- 入库：FP-021
```
或
```markdown
- 入库：skills/t2h-ohos-port/references/pitfalls.md#13
```

然后跑：

```bash
lingqu-cli notes --action archive --path <工程>
```

效果：带 `- 入库：…` 的条目被挪到 `<工程>/.lingqu/notes/<工程>-archived.md`（**归档不删证据**），
主文件只留待裁决的；`suggest` 下次就不会再把它当候选提出来（避免重复 PR）。

> 标记是**人**打的，不是机器打的——这正是"人裁决"的落点。打标记这个动作本身很便宜（一行），
> 但它把"已沉淀"和"还没沉淀"分开了。

## 5. 命令速查（阶段 1 全部能力）

```bash
# 1) 看这个工程攒了多少条经验
lingqu-cli notes --action list --path <工程>

# 2) 写一条（内容走文件：中文不能过 argv，见 AGENTS.md §4-119）
cat > note-in.json <<'EOF'
{"title":"hvigor 00308018 不是签名问题","symptom":"t2h:hap 报 00308018，日志里是 cargo tauri panic",
 "cause":"hvigorfile 的 tauri 钩子在非 dev 场景必然失败","repro":"juCang 工程跑 t2h:hap",
 "fix":"R2-PORT-015 注掉 .afterRun(buildRustCode)"}
EOF
lingqu-cli notes --action append --path <工程> --body note-in.json

# 3) 筛候选 + 出 PR 草稿（默认写到 <工程>/.lingqu/notes/<工程>-candidates.md）
lingqu-cli notes --action suggest --path <工程>
lingqu-cli notes --action suggest --path <工程> --out docs/skills-候选.md   # 指定输出位置

# 4) 入库后归档
lingqu-cli notes --action archive --path <工程>

# 5) 整份经验导出（给报告/人看）
lingqu-cli notes --action export --path <工程>
```

`suggest` 的回包（只看关键字段）：

```json
{
  "ok": true,
  "candidateCount": 2,          // 经验候选（次数 ≥2 + 四段齐 + 未入库）
  "missCandidateCount": 1,      // 未命中指纹候选（同签名 ≥3 次）
  "lessonTotal": 5,             // 这个工程一共记了多少条
  "missLedgerLines": 14,        // 未命中台账当前行数
  "out": "…/.lingqu/notes/juCang-candidates.md",
  "candidates": ["hvigor 00308018 不是签名问题", "……"],
  "missCandidates": [ { "sig": "error: boom", "times": 4 } ]
}
```

`archive` 的回包：

```json
{
  "ok": true,
  "archivedNotes": 1, "keptNotes": 4,
  "archivePath": "…/.lingqu/notes/juCang-archived.md",
  "notesNote": "ok:归档 1 条，主文件保留 4 条",
  "missLedgerLines": 14,
  "missNote": "台账 14 行，未到 200 行阈值，不归档"
}
```

**台账滚动**：`misses.jsonl` 到 **200 行**（`MISS_ROLL_MIN_LINES`）时 `archive` 会把它整体挪到
`.lingqu/diagnose/misses.<时间戳>.jsonl` 再清零当前台账——**先写归档件、成功后才动台账**，不丢证据。
语义上这是"这一轮查清了"的分界线：补完指纹后同签名**应当停止增长**。

## 6. 反例清单（看到就退回）

| 反例 | 为什么不收 |
|---|---|
| 「可能是 X 导致的」这类**推测** | 根因栏不许编；不确定就写"未定位到确切机制" |
| 只出现 **1 次** 且无法复现 | 大概率是命令/环境的一次性抖动，进库会污染规则 |
| 夹带**本机信息**：用户路径、UDID、项目名、密钥 | 技能库是公开资产；贴出去等于泄密（见 `SECURITY.md`） |
| 把**第三方工具的 bug** 写成"我们的修法" | 该进指纹（识别）或上游回馈（修），不是技能 |
| 与已有条目**重复** | 先 `grep` 报错原文；重复就合并、次数累加，别新开一条 |
| 修法依赖**未提交的本地改动** | 别人照抄会失败；要么把依赖也沉淀，要么写清前置条件 |
| 把整段日志粘进条目 | 只留稳定子串；长证据留在 `.lingqu/<步骤>/<工程>.log` 里引用 |

## 7. PR 前复核清单

- [ ] 三条件都满足（次数 ≥2、四段齐全、未入库）——`suggest` 已经筛过，别手工放行不达标的
- [ ] 三追问都答得上（实测 / 跨样本或标注单样本 / 属于本工具该管的）
- [ ] 新条目格式与 `pitfalls.md` 既有条目**一致**（`### N.` + `- **根因**` + `- **修法**`），放在正确分节、编号续上、头部索引同步
- [ ] 写了**实测出处**（样本 / 命令 / 落档路径 / 日期）
- [ ] 全文 `grep` 过：无本机绝对路径、无 UDID、无密钥、无项目私有信息
- [ ] 若做成指纹：marker 是稳定子串，**配了单测**（命中 + 不该命中的两侧）
- [ ] 若做成规则：有 auto/guide 分档、进 `revertPairs()`、有单测
- [ ] 合并后回到工程打 `- 入库：<引用>` 并跑一次 `notes --action archive`
- [ ] `CHANGELOG.md` / 相关文档同批更新（`AGENTS.md` §5）
