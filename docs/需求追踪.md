## 五、验收风险清单（**60 分口径**，2026-11-03 用户评估）

> **口径校准**：工程能力实现约 95%，但按验收原文的严格口径（"能用"而非"能跑"、闭环实证
> 而非"机制完成"）当前综合 **60 分**。以下三项是把分数推上去的**验证任务**（不是新功能开发），
> 每完成一项按其及格判据重估。任何"已验证"标注在三项清账前都按此口径打折看待。

### R-1 飞轮闭环实证（对应 A1/A3 附加口径，当前证据为零）

**问题**：机制代码完成 ≠ 闭环验证。agent 在**无人为干预**的一轮迁移里，是否真的自己调
`notes` 落档、撞坑后走 diagnose→攒签名→候选、**自主提交 PR**——样本量 1，且 `canSubmit=true`
路径的 token 从未真发过（PR 提交证据为零）。

**任务**：挑一个新样本（rust-music 为现成第 4 个），**全程零人工干预**跑一轮迁移，事后只验三件事：

| # | 验证点 | 及格判据 |
|---|---|---|
| 1.1 | agent 自写经验 | `.lingqu/notes/<工程>.md` 有 agent 自落的四段式经验（非人工代写），次数累加正常 |
| 1.2 | 未命中自动攒证据 | `misses.jsonl` 出现本轮新签名（diagnose 接不住的报错被台账接住） |
| 1.3 | 自主提交 PR | 配置 `LINGQU_GITCODE_TOKEN` 后，候选在**无人点击**的情况下真发 PR 到技能库仓（人只做合并评审） |

**升档条件**：三件事全部发生，且**下一个样本的轮次/人工介入数可观测下降**（飞轮"越用越强"被观测到，而非被声明）。

### R-2 规则库压力测试（对应 C2/C3 出口判据，当前样本量 3）

**问题**：15 条规则 + 20 条指纹全部来自 **3 个样本**的归纳；615+ 表外 crate"默认直编"零实证；
C2 置信度仅 1 个基线（habit-tree）；"不可用清单与真实编译失败吻合 ≥80%"**一次都没执行过**。

**任务**：每推一个新样本，先盲跑 `deps`+`diagnose` 出预测，再跑真实交叉编译对照——按
[`docs/P3-出口判据1-验证方案.md`](P3-出口判据1-验证方案.md) 的口径记 Recall/Precision；
**每个 FN/FP 逐条回填规则/指纹**（不允许"解释过去就算"）。

**及格判据**：累计 ≥3 个新样本的对照数据；Recall ≥80%（判据 1 真正执行过）；所有 FN/FP
都有入库记录（新指纹 / 修规则 / 样本特有三分类）。

### R-3 鸿蒙原生能力位矩阵（对应 A4 口径修正，**当前最大的口径缺口**）

**问题**：鸿蒙侧当前仅"**能运行**"（ArkWeb 渲染 + 启停成功），**原生能力位未验证**——
例如**文件选择框在鸿蒙侧当前不可用**。habit-tree verify 的"100% 可用率"统计的是
**工程自报的 6 项窄清单**，不代表全量原生能力；"核心功能可用率 ≥80%"在真实验收里
会被这个口径击穿。

**任务**：把 verify 清单从"工程自报"扩成**系统能力位全量矩阵**，逐项在真机实测：

| 能力域 | 待验项（初稿，逐样本补全） |
|---|---|
| 文件系统 | **文件选择框**（已知鸿蒙侧不可用）、保存对话框、沙箱读写 |
| 系统 UI | 通知、托盘、全局快捷键、窗口管理（多窗/置顶） |
| 数据与凭据 | 本地数据库（redb/SQLite）、OS keychain 类凭据存储 |
| 媒体 | 音频播放/录音、相机、屏幕录制 |
| 网络 | HTTP 流式（SSE）、WebSocket、自定义协议 |
| 系统交互 | 剪贴板、分享、 deep link / 协议唤起、权限弹窗流 |

**及格判据**：能力位矩阵落库（每项：Windows 现状 / 鸿蒙实测结果 / 差异处置）；
每个已验样本的 `verify` 按新口径重出数字；"不可用"项如实进报告的「没做什么」与已知限制。

### 执行顺序建议

R-3 与 R-1 可在**同一个样本轮**里同时取证（rust-music：零干预跑轮 → 验 1.1/1.2/1.3 →
同时过能力位矩阵）→ R-2 随每个新样本持续积累。三项清账后重估综合分。
