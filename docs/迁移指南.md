# 迁移指南：把你的 Tauri 应用搬到鸿蒙 PC

> 面向**想把一个真实 Tauri 应用迁到鸿蒙 PC** 的使用者。方法论与坑的完整版见
> [`skills/t2h-ohos-port/SKILL.md`](../skills/t2h-ohos-port/SKILL.md)（给 agent 的技能，人读也一样有用）；
> 本指南讲的是**用灵渠怎么走完这条流程、每一步信什么、卡住了怎么办**。
> 三个已验证样本：habit-tree（真机 100%）· m3u8dl-tauri（真机 100%）· juCang（真机 85%）。

---

## 0. 开始之前

| 前置 | 说明 |
|---|---|
| 仓颉 SDK 1.0.5 + stdx + [cj-tauri 框架仓](https://atomgit.com/qq8864/cj-tauri) | 环境变量表见 [`docs/开发环境.md`](开发环境.md)；`./scripts/setup.sh` 只体检不改文件 |
| 模型 Key（AI 路径才需要） | `DEEPSEEK_API_KEY` / `OPENAI_API_KEY` 等；规则路径不需要 |
| 目标工程 | 标准 Tauri 2 工程（`src-tauri/` + 前端）；非标准结构先跑 `scan` 看容错 |
| 鸿蒙 PC / 真机（验证步骤才需要） | hdc 可用；自动签名走 AGC（`sign --auto`，浏览器授权一次） |

**先跑一次体检**：`./scripts/test.sh -s` 六项全绿再开工——工具自身不可信时，迁移结论都不可信。

## 1. 第一眼：迁移画像（先算清楚，再动手）

```bash
lingqu-cli scan --path <工程>    # 五类清单 + 评分 + 覆盖率（C1/C2/C3）
lingqu-cli deps --path <工程>    # Cargo 依赖 → OHOS 兼容矩阵 + 替代建议
```

读画像时看三处：

1. **C1（结论覆盖率）**：每一项都必须有处置结论（改造/降级/不适用/人工）——出现"未知"说明扫描器没跟上，别硬跑；
2. **C2（发现置信度）**：与人工基线双向 diff 的结果。有基线的样本才显示，没有就是"未对照"（不编 100）；
3. **阻塞项**：`hard`（未知项，先解决再继续）与 `soft`（人工项，给位置给方案）。

**依赖矩阵是分档不是判决**：可用（含有条件可用，evidence 写清条件）/ 需 patch（给 git rev 与钉法）/ 不可用（给替代）。
`tauri` 全家桶、`wry`、`tao`、`openharmony-ability` 必须换 fork；`openssl-sys`/`native-tls`/`rfd` 不可用给替代；
`reqwest`、`dirs` 这类"有条件可用"的 evidence 一定要看——**编译过得去 ≠ 运行时没坑**。

## 2. 八步流水线（每步信什么）

```bash
lingqu-cli port   --path <工程>            # 17 条规则改造（幂等 / 可回滚 / 决策可审计）
lingqu-cli build  --path <工程>            # 交叉编译 + .so 前端指纹闸
lingqu-cli hap    --path <工程>            # HAP 装配（点名校验 lib<module>.so）
lingqu-cli sign   --auto --path <工程>     # AGC 自动签名
lingqu-cli deploy --path <工程> --start    # hdc 装机 + 拉起 + hilog
lingqu-cli verify --path <工程>            # 功能清单 → 可用率
lingqu-cli report --path <工程>            # 三段式报告 + 风险分级
# 或一条命令：lingqu-cli migrate --path <工程> --wait
```

| 步骤 | 信什么 | 最容易踩的坑 |
|---|---|---|
| port | 每条规则有 id 与 before→after；幂等（二次跑全跳过）；`t2h:revert` 可整体回滚 | 规则覆盖不到的（confirm/prompt 调用点、type=color）走 **guide 档**——给位置给方案，别机械替换 |
| build | **`.so` 前端指纹闸**：`.so` 内嵌 AssetKey ↔ `dist/` 比对 | 改前端必须重编 `.so`——只重打 HAP 无效（见 §4 坑 1） |
| hap | 点名校验 `lib<module>.so` 在 `libs/arm64-v8a/` | Windows 上 `cargo tauri ohos build` 装配失败是预期，转 hvigor 手工装配 |
| sign | `signed=true` + 协议文本 | **调试用 debug 签名**；release profile 直装报 `9568322 not trusted app source`；上架前改回 |
| deploy | 按**输出文本**判（`install bundle successfully` / `start ability successfully`），不按退出码 | `hdc file send` 要 cd 到 HAP 目录再发文件名（`9568269` 的坑） |
| verify | 功能清单三态（通过/失败/未验证）+ 每条证据（截图/hilog/dumpLayout） | 白屏先查 `custom-protocol` feature，再查 AssetKey（.so 旧），再查 `withGlobalTauri` |

**人工介入的口径**：规则覆盖不到的走 guide 档，每处都要你决策（采纳/忽略），决策落
`.lingqu/port/<工程>/decisions.json`——验收线是**单应用 ≤5 处**，逐条可审计。
三个样本实测：juCang 只需 1 处。

## 3. 两条路径：规则先行，AI 兜底

**规则路径**（确定性，零 token）：上面 8 步 CLI 就是。可枚举的机械改动（Cargo.toml 钉版、
patch 段、工具链、lib.rs 注入、localStorage polyfill、对话框资源）全部规则化——17 条规则，
每条带 evidence 与出处。

**AI 路径**（长尾兜底）：GUI 里「🤖 开始 AI 自动迁移」（`t2h:autoport_start`）——
任务书交给内置引擎 cjh，它自己跑流水线；**停滞 / 超预算才叫人**，人工介入逐次记录。
agent 是执行者，工具（`t2h:*`）是它的手（ADR D-015）。

**诊断在中间**：构建/运行报错先喂给指纹库——

```bash
lingqu-cli diagnose --logPath <构建日志>
```

命中即给「现象 → 根因 → 修法」（rule 档直接建议重跑 `port`，幂等只补缺口），**不调模型**；
未命中如实返回空，这时才把日志粘给右栏 AI 对话（长尾）。

## 4. 高频坑速查（按报错/现象索引）

完整版 22 条指纹见 `t2h:diagnose` 与 [`skills/t2h-ohos-port/references/pitfalls.md`](../skills/t2h-ohos-port/references/pitfalls.md)。

| 报错 / 现象 | 根因 → 修法 |
|---|---|
| `cannot find crate napi_ohos` | 缺 OHOS target 段 napi 桥 → 规则 005 自动补 |
| `-lgcc_eh` not found（Windows） | GNU 工具链不适配 → gnullvm（规则 007） |
| 链接器找不到 / NDK clang 跑不动 | NDK 自带 clang 是 shell 脚本 → 规则 008 直指 `llvm/bin/clang` |
| patch 了 tauri 却还在编官方版 | `^` 版本解析绕过 patch → 钉 `=2.11.5`（规则 002） |
| 真机始终旧界面 / 版本号不变 | **前端嵌在 .so 里，rawfile 是死资源** → 重编 `.so`，用 AssetKey 指纹核对 |
| `9568322 not trusted app source` | release 分发签名直装 → 切 debugKey，上架改回 |
| `9568269 install file path invalid` | hdc 保留目录结构 → cd 到 HAP 目录再 send |
| `10106102`（启动失败） | 真机锁屏 → 手动解锁（脚本留等待点） |
| 白屏 | custom-protocol 缺 → devUrl localhost 被加载；按 verify 三查顺序排查 |

## 5. 卡住了怎么办（三级递进）

1. **查指纹**：`lingqu-cli diagnose --logPath <日志>`——20 条已固化的坑，命中即修，不调模型；
2. **问 AI**：右栏对话把日志粘给 cjh（工作台内置，会话可断点续迁）；它的技能库
   （`t2h:skill` 装进 `~/.cjh/skills/`）就是这份指南的 agent 版；
3. **fork 先行**：确认是 tauri / openharmony-ability 本身的能力缺口——**不等上游**，
   在 [yangyongzhen/tauri](https://github.com/yangyongzhen/tauri) 或
   [openharmony-ability](https://github.com/yangyongzhen/openharmony-ability) 建分支
   （`fix/<工程>-<问题>`）先解决，patch rev 钉住继续移植，**后续整理 PR 贡献回上游**。
   cc-switch（官方 feat/open-harmony）与 habit-tree（ability feat/0.3.0 patch）都是这条路的实证。

## 6. 迁完之后：报告、断点与飞轮

- **报告**：`lingqu-cli report --path <工程>`——三段式（做了什么 / 没做什么 / 需要你做什么）+
  风险分级；全部只读落档生成，**报告里每个数都能追溯到 `.lingqu/` 下的证据文件**；
- **断点续迁**：改了前端 → `.so` 自动判过期 → 任务退回构建步，不假装成功；
- **经验回填（飞轮）**：agent 迁移中撞坑会自己写经验（`<工程>/.lingqu/notes/<工程>.md`，
  四段式）、未命中指纹自动进台账（`diagnose/misses.jsonl`）。**你负责裁决**：

```bash
lingqu-cli notes --action suggest --path <工程>   # 攒够次数的候选 + PR 正文草稿
lingqu-cli notes --action archive --path <工程>   # 已入库条目移出候选池
```

  裁决通过的指纹/规则/技能进库后，**下一个应用自动吃上**——这是灵渠与传统工具的根本区别：
  迁移量越大，工具越强（详见 [`docs/AI自进化飞轮.md`](AI自进化飞轮.md)）。
