# 自动签名实战复盘（路线 A：AGC 云生成）

> **这份文件是什么**：把「让 `com.atomgit.m3u8dl_tauri` 在鸿蒙 PC 上从**完全没有签名**走到
> `signed=true` 且 **`install bundle successfully`**」这一整条路，连同**六个把人卡住的坎**
> 和**每个坎的可判定判据**，完整写下来。
>
> 读者对象：① 下一个接手的 AI agent（第 5 节是可直接照抄的操作手册）；② 将来要加新包名 /
> 换机器 / 换账号的人（第 6 节是清单）；③ 只想知道"到底怎么回事"的人（第 1–2 节）。
>
> **实测环境**：鸿蒙 PC `3QC0124B20000048`（HarmonyOS，`deviceType=4`）· DevEco 6.1 · hvigor 6.24.4 ·
> hdc 3.2.0d · 仓颉 1.0.5.1 · 2026-11-02。
>
> 相关文档：机制研究见 `docs/鸿蒙自动签名机制.md`；离线配方见

## 0. 结论先讲（TL;DR）

1. **能自动做，且不需要打开 DevEco**：一条命令
   `lingqu-cli sign --auto --path <工程>` 完成「团队 → 设备 → 密钥对/CSR → 证书 → debug profile →
   写材料 → 写回 `build-profile.json5`」，之后 `hap` 出签名包、`deploy` 装进真机。
2. **但"一次浏览器授权"省不掉**——那是华为 OAuth 的硬约束（loopback 回调）。
   之后令牌加密存在 `~/.lingqu/agc/`，**不需要每次登录**。
3. **私钥永不出本机**：上云的只有 CSR 与包名/UDID；`.p12` 从不离开本机。
4. 真正的难点**不在密码学，也不在协议**，而在**六处"名字对得上但语义不对"**：
   同名证书过期、证书配额被过期件占满、换密钥后旧证书绑旧公钥、配置非空被自己的保护挡住、
   旧 `.p12` 口令无人知道、同包名装过异签名版本。这六处全部在本文第 3 节。

## 1. 全链路：每一步在哪、凭什么算成功

```
① 浏览器授权（人点一次）
   localhost 回环服务 ←302─ 华为登录页 ──► /callback?code=&tempToken=&siteId=
        ↓ 校验 Host/白名单（code 只核对不拒绝）
② tempToken → JWT：authrouter/auth/api/temptoken/check
   ③ JWT 校验：authrouter/auth/api/jwToken/check  → userId / accessToken / countryCode
        ↓ 令牌 AES-128-GCM 加密落盘（~/.lingqu/agc/）
④ 团队：GET /api/ups/user-permission-service/v1/user-team-list      → 取 teamId(40574614)
⑤ 设备：GET /api/cps/device-manage/v1/device/list?encodeFlag=0&start=1&pageSize=100
        └ 没有本机 UDID 就 POST /api/cps/device-manage/v1/device/add（udid 大写 + deviceType）
⑥ 密钥对（**本地**）：hap-sign-tool generate-keypair → <base>=.p12（随机口令，不进日志）
   CSR（**本地**）：hap-sign-tool generate-csr       → <base>=.csr
⑦ 证书：GET  /api/cps/harmony-cert-manage/v1/cert/list     → 按"有效期"挑可用
        ├ 没有可用 → POST /api/cps/harmony-cert-manage/v1/cert/add（csr + certName + certType=1）
        └ 配额满 → DELETE /api/cps/harmony-cert-manage/v1/cert/delete（{"certIds":[…]}）
        ↓ 用 objects/url/reapply 换签名下载链 → curl 原样取字节 → sha256 校验 → <base>=.cer
⑧ profile：POST /api/cps/provision-manage/v1/ide/test/provision/add
        { certList:[<certId>], packageName:<bundleName>, provisionName:<sha256 前 16>, deviceList:[<**云端设备 id**>] }
        ↓ 同样换下载链 → 落地 <base>=.p7b（PKCS#7，内含 JSON）
⑨ 口令密文：用本机 ~/.ohos/config/material 的 workKey 做 AES-128-GCM
        → 写成 hvigor 认的十六进制串（storePassword / keyPassword）
⑩ 写回 build-profile.json5（先 .bak）：material{storeFile,certpath,profile,keyAlias,signAlg,…}
        └ products[0].signingConfig 指向它
⑪ hvigor assembleHap → Finished :entry:default@SignHap → entry-default-signed.hap
⑫ hdc install -r → 输出含 `install bundle successfully`（**别看退出码**）
```

**材料命名必须与 DevEco 逐字节一致**（否则 hvigor 的自动签名逻辑不认，人也对不上历史材料）：

```
<safeProduct>_<工程目录名>_<base64url(sha256(前向斜杠路径)) 去掉'='>=
        ↑ 后缀 .p12 / .csr / .cer / .p7b
实测：default_ohos_cqJPvSnvtx180vSdtiz2zma7G33SCwXOJ8Oae_Omf0Y=.p12
```

> ⚠️ 注意结尾那个 `=`：它是命名规则的一部分（base64url 去掉 padding 后又补了一个分隔用 `=`）。
> 拼路径时**手抄模板漏掉它** → `exists()` 全 false → 工具"静默什么都不做"（第 3.6 节）。

## 2. 关键协议细节（都是实测出来的，不要按猜的写）

### 2.1 请求头与成功判据

| 项 | 值 |
|---|---|
| 三件套头 | `uid` = userId、`teamId` = 团队 id、`oauth2Token` = accessToken |
| 成功判据 | **HTTP 200 不算成功**——必须看响应体 `ret.code == 0` |
| 错误文案 | 取 `ret.msg`（可能是对象，也可能是被 JSON 编码过的字符串） |

### 2.2 端点与参数形状（踩过才敢写）

| 动作 | 方法 | 路径 | 参数位置要点 |
|---|---|---|---|
| 设备列表 | GET | `/api/cps/device-manage/v1/device/list` | `?encodeFlag=0&start=1&pageSize=100`；**响应数组字段名是 `list`**（不是 `devicesInfo`/`devices`/`deviceList`/`deviceInfos`——四个都不是） |
| 设备注册 | POST | `/api/cps/device-manage/v1/device/add` | `{deviceName, udid(大写), deviceType}`；`205389858`=UDID 已存在（**按已注册处理**）、`205389857`=名字重复（换 nonce 重试一次） |
| 证书列表 | GET | `/api/cps/harmony-cert-manage/v1/cert/list` | 响应 `certList[]`，每条有 `id / certName / certObjectId / expireTime / status` |
| 证书新建 | POST | `/api/cps/harmony-cert-manage/v1/cert/add` | `{csr(PEM 文本), certName, certType}`，`certType`：1=debug / 2=release |
| **证书删除** | **DELETE** | `/api/cps/harmony-cert-manage/v1/cert/delete` | **参数必须放请求体** `{"certIds":["<id>"]}`，且**必须带 Content-Length**。放 query（`?certIds=`、`?certIds[]=`、JSON 编码）一律被回 `... Parameter is [reqParams]. Processor is [body]. Message is [Body parameter is required.]` |
| debug profile | POST | `/api/cps/provision-manage/v1/ide/test/provision/add` | `{certList:[id], packageName, provisionName, deviceList:[**云端设备 id**]}`；`provisionName` = `sha256("default_"+bundle+"_"+bundle)` 前 16 位（与 DevEco 一致） |
| 换下载链 | POST | `/api/amis/app-manage/v1/objects/url/reapply` | `{"sourceUrls":"<对象 URL>"}`（**单个字符串**，不是数组）→ 响应 `urlsInfo[0].newUrl + sha256` |
| 删除 profile | POST | `/api/cps/provision-manage/v1/provision/delete` | 下载完就删，省配额 |

### 2.3 三个容易搞错的字段

1. **`deviceList` 要的是"云端设备 id"，不是 UDID。**
   传 UDID（64 位十六进制）会被回
   `signIdeTestProvision.reqParams.deviceList[0].<list element>: size must be between 0 and 32`。
   → 先 `device/list` 把 `id` 收集起来。
2. **证书可用性看 `expireTime`/`status`，不看名字。**
   实测同一账号：`yangTest`（status=2，2025-07 过期）、`auto_debug_40574614.cer`（status=2，
   2026-06 过期）、`agc_1771850782319`（status=2，2026-08 过期）、`yang_release`（status=1，2029 到期）。
   拿过期的去申请 → `The certList is invalid.`（`205389848`）；拿 release 证书去申请 debug →
   `provisionType does not match certType`。
3. **证书下载链是 SigV4 签名 URL，通用 HTTP 客户端取会 403。**
   表现为：同一 URL 用系统 `curl` 拿到 2914 字节，用自己的 HTTP 客户端 403——
   因为客户端会重新编码 query（`%2F` 之类），签名就失效了。
   → 项目里改成 `curl -sS -L -f` 原样取字节，再自己校验 sha256（`agcDownloadObject`）。

### 2.4 口令密文（AesGcmKit 兼容）

仓颉 std/stdx 1.0.5.1 **没有 AES**（只有 SM4，且本机 SM4-GCM 不可用），所以自己实现了
AES-128-GCM（`src/compiler/aes_gcm.cj`，NIST SP 800-38D 向量 + 本机 Node/OpenSSL 互证）。

| 项 | 值 |
|---|---|
| workKey | `PBKDF2-HMAC-SHA256(lossyUtf8(XOR(fd/0, fd/1, fd/2, FIXED16)), salt, 10000, 16)`，材料在 `~/.ohos/config/material/`（`ac` / `ce` / `fd/0,1,2`） |
| FIXED16 | `31 f3 09 73 d6 af 5b b8 d3 be b1 58 65 83 c0 77` |
| 载荷 | `[长度(4 字节大端 = 密文长+16)][IV(12)][密文][tag(16)]` 依次拼接，输出**十六进制字符串** |
| 谁能解 | **hvigor 能解**（0.39.16 起有硬证据：把 habit-tree 的密文换成我们造的 → `Finished :default@SignHap` + `BUILD SUCCESSFUL`） |

**"能不能沿用旧密文"的判据不是猜**：跑 `sign --reencrypt --buildProfile <path>`，
解不开就是 `GCM tag mismatch` —— 说明那份密文与本机 `material/` 不配套，必须换材料。

## 3. 六个坎（现象 → 根因 → 排查 → 处置）

> 这一节是本文的核心。六个坎的共同点：**报错信息离真正原因很远**，靠"猜 + 试"会绕很久。

### 3.1 坎一：证书名字对得上，但它已经过期

- **现象**：`cert/list` 里明明有 `auto_debug_40574614.cer`，申请 profile 却回
  `AGC 错误 205389848：The certList is invalid.`
- **根因**：这张证书 `status=2`、`expireTime=1781883409000`（2026-06-19），今天已经是 2026-11-01。
  AGC 的调试证书大约半年有效，过期后**依然留在列表里、名字也还叫那个名字**。
- **排查**：把 `cert/list` 每条打印出来，比对 `expireTime` 与当前时间——不要只 grep 名字。
- **处置**：证书选择改成"按有效期挑"（`AgcCert.usable()` + `findUsableCert`）；
  没有可用的就走新建。
- **通用判据**：**任何"按名字查找"的外部资源，都要再确认一次"它此刻是否仍然有效"**
  （证书看有效期、设备看状态、token 看过期时间）。

### 3.2 坎二：证书配额被过期件占满

- **现象**：新建证书回 `205389872：[AppGalleryConnectProvisionService]certificate number exceeds limit.`
- **根因**：AGC 调试证书有数量上限（本账号实测 **4 张**），**过期件照样占名额**。
  当时 4 张里 3 张已过期。
- **排查**：数 `certList` 条数 + 数其中已过期的。
- **处置**：先删再建。删除有坑（见 §2.2 最后一行：**DELETE + 请求体 + Content-Length**）。
- **安全边界**：只删"已过期 **且** 名字以 `auto_debug_` / `auto_release_` 开头"的
  （`staleCertsOf`）——用户手工在控制台建的证书**一律不碰**，宁可报错让人决定。
- **通用判据**：配额型资源要写"**腾位置**"这条路径，并且**限定可删除的集合**。

### 3.3 坎三：换了密钥对，云端同名证书绑的还是旧公钥

- **现象**：证书建好了、profile 也拿到了，但 hvigor 侧签出来的东西与 `.p12` 不匹配
  （后续表现为签名验证失败/`00303242`）。
- **根因**：证书是**由 CSR 签发**的，CSR 来自 `.p12` 里的密钥对。换了密钥对却复用云端
  "同名证书" → profile 里的 `development-certificate` 是**旧公钥**的证书。
- **处置**：`--newKeys` 时先删同名证书再新建；**并且强制重下本地 `.cer`**
  （本地那份对应旧证书，不重下就是"新 id + 旧文件"）。
- **通用判据**：**证书的身份是公钥，不是名字**。任何"资源实体换了但标识没换"的场景都要显式失效缓存。

### 3.4 坎四：写回被自己的保护挡住

- **现象**：`⑦ 写回失败：工程里已经有非空的 signingConfigs，不做覆盖（要重配请先手动清空）`
  ——整条链死在最后一步。
- **根因**：早期实现为了避免覆盖 DevEco 写的配置，规定"`signingConfigs` 非空就拒绝"。
  但**复用同一个 `.p12` 时，`.p7b/.cer` 会因为证书换发而变**——"已有配置"不等于"配置是对的"。
- **处置**：新增 `replaceOwnSigningConfigs`——**只有当工程里那份 `storeFile` 就是我们要写的
  同一个 `.p12`** 时才就地更新（换材料仍然拒绝并说明）。
  定位数组要**按深度配对并跳过 json5 字符串**（早期"遇到第一个 `]` 就停"只在空数组上成立）。
- **通用判据**：保护性判断要区分"**别人的东西**"与"**我自己的旧东西**"，
  一律"非空就拒绝"会把幂等重跑变成不可能。

### 3.5 坎五：`.p12` 的口令没人知道

- **现象**：hvigor 报
  `00303242 Signature material verification failed, as: Unsupported state or unable to authenticate data`；
  `sign --reencrypt` 报 `口令解密失败：GCM tag mismatch`。
- **根因**：那套材料是**从别处拷来的 / `material/` 重建过**的，`.p12` 的口令随材料一起丢了。
  我们既解不开旧密文，也就没法用本机 workKey 重新加密 → hvigor 拿到的是解不开的密文。
- **排查**：`--reencrypt` 失败 ≠ 我们的实现有问题，而是**这份密文与本机 material 不配套**。
  两种"不配套"要分清：密文是**别人的 key** 加的（`GCM tag mismatch`），
  还是密文能解但**口令与 p12 不一致**（那会表现成签名失败而不是解密失败）。
- **处置**：`--newKeys`——把旧材料**改名留底**（`.lingqu-bak-<毫秒>`，私钥不可再生，绝不直接删），
  重新生成自己掌口令的密钥对，走完整链。
- **通用判据**：**拿不到明文口令就换材料，不要猜口令**。猜口令是"看起来能过、实际上随机失败"的最坏形态。

### 3.6 坎六：`--newKeys` "什么都不做"（静默失效）

- **现象**：加了 `--newKeys` 跑完，输出里仍是「④ 复用本地已有密钥」，一个文件都没被挪走，
  也没有任何报错。为此排查了近一小时。
- **根因**：手抄路径模板时**漏了命名规则里的 `=`**：
  `"${configDir}/${base}${suffix}"` 得到 `…Omf0Y.p12`，而真实文件是 `…Omf0Y=.p12`。
  `exists()` 全 false → 循环体全被 `continue` 跳过。
- **处置**：把四种材料的路径收成**唯一构造点** `matPrefix = "<configDir>/<base>="`，
  再拼后缀；并在 eprintln 里回投开关的真实取值（`newKeys=true/false`）。
- **通用判据**：**同一组路径只能有一个构造点**。凡是"开关打开却没反应"，
  第一步是**打印它读到的值**，而不是怀疑取值逻辑。

### 3.7 附带撞到的：装过异签名的同包名版本

- **现象**：`hdc install` 报 `9568332 install sign info inconsistent`。
- **根因**：设备上已装过这个包名的应用，且**用的是另一套签名**（换材料后必然如此）。
- **处置**：`bm uninstall -n <bundle>` 后重装。`deploy` 现在遇到 `9568332` 会**自动卸载并重试一次**，
  并把这次动作写进证据（`installDetail` 追加"（先卸载了旧签名的同包名版本）"）。
- **另一类易混**：`10106102` 是**设备锁屏**（开发者模式下禁止自动解锁），处置是"解锁后重试"，
  与 ability 名/bundle 名无关——结论文案已按这个区分开（原来一律怪"ability 名写错"，误导过一轮）。

## 5. 操作手册（下一个 agent 直接照抄）

### 5.1 前置体检（10 秒，别跳过）

```bash
lingqu-cli sign --tool-check          # java / hap-sign-tool.jar / hdc 是否都在、能不能真生成一对密钥
lingqu-cli sign --path <工程>          # 离线判定：本机有没有能装这台设备的材料
hdc shell bm get --udid               # 记下 UDID（后面 p7b 里要能看到它）
```

### 5.2 一次授权（唯一的人工介入点）

```bash
lingqu-cli sign --login               # 起 loopback 服务并打开登录页；用户在浏览器点授权
# 成功标志：命令行出现 user=… uid=… country=CN … tokenSaved=true
# 令牌落在 ~/.lingqu/agc/{keys/kek.bin, token.enc}（AES-128-GCM），后续不需要再登录
```

> 排障两条：
> ① 回调页上**直接点它给的登录链接**（`/callback` 是内部地址，手动打开必然报错）；
> ② 证据在 `~/.lingqu/agc/login-callback.log`（记 code 长度、siteId、是否匹配，**不记 tempToken 明文**）。

### 5.3 自动签名 + 装配 + 装机

```bash
lingqu-cli sign --auto --path <工程>            # 复用本机材料
lingqu-cli sign --auto --newKeys --path <工程>  # 材料来路不明/口令丢了时用这个
lingqu-cli hap    --path <工程>                 # 期望 signed=true
lingqu-cli deploy --path <工程> --start         # 期望 installed=true、started=true
lingqu-cli verify --path <工程>                 # 可用率与证据链落 <工程>/.lingqu/
```

### 5.4 出错了按这个顺序看

1. **哪一步**：`AutoSignOutcome.steps` 每行一步，失败会指到步骤号（②③④⑤⑥⑦）。
2. **是不是"名字对但语义不对"**：证书 → 看 `expireTime`；密钥 → 看是不是换了密钥对；
   配置 → 看 `storeFile` 是不是同一个 `.p12`。
3. **密文配不配**：`sign --reencrypt --buildProfile <path>`，`GCM tag mismatch` 就说明要换材料。
4. **装机失败码**：`9568322` 签名不被信任（profile 缺本机 UDID / 非 debug）；`9568332` 装过异签名版本；
   `10106102` 锁屏。
5. **hvigor 失败码**：`00303074` 包名与 profile 不一致；`00303242` 口令密文解不开；`00303107` 材料文件缺失。

## 6. 复用清单（换机器 / 换账号 / 换包名）

| 场景 | 要做的事 | 为什么 |
|---|---|---|
| **换包名** | 直接 `sign --auto --path <新工程>` | profile 按包名签发，工具会为新包名申请新的；证书可复用 |
| **换机器**（同一账号） | `sign --login` 重新授权 → `sign --auto` | 令牌是本机加密落盘的；新机器的 `material/` 不同，旧密文不可用 |
| **换机器**（`.ohos` 是拷过来的） | `sign --auto --newKeys` | 拷来的 `.p12` 口令无人知道（§3.5） |
| **换账号 / 换团队** | 重新 `--login`；旧证书留在旧团队里（不影响） | 证书与设备都挂在团队下 |
| **证书撞配额** | 工具会自动删"自己的过期件"；若被用户手工证书占满 → 去 AGC 控制台删 | 安全边界：不替用户删他建的东西 |
| **`material/` 被重建** | 所有旧密文失效 → 逐个工程 `--newKeys` 或 `--reencrypt`（能解就 reencrypt） | workKey 变了 |

## 7. 边界与已知限制（不要当成 bug 反复查）

1. **一次浏览器授权不能省**。loopback 授权是华为侧的流程；能省的是"每次都要点"。
2. **令牌会过期**。过期后 `agcTeamList` 拉不到 → 报"token 可能已失效，重跑 `sign --login`"。
3. **证书配额**（本账号 4 张）是账号级硬限制，过期件占位。
4. **`--newKeys` 会消耗一次证书配额**（删旧建新，净占用不变，但要小心并发）。
5. **`deviceList` 上限**：元素长度 ≤32（所以只能放云端 id）；团队设备数也有上限。
6. **`hdc install` 退出码永远是 0**，只能按输出文本判成败（§4-40）。
7. **锁屏状态无法自动解锁**（开发者模式）——这是 A3「人工介入」的一部分，不是工具缺陷。
8. **仓颉没有 AES**：想复用我们的实现就照 `src/compiler/aes_gcm.cj`（已用 NIST 向量 + Node/OpenSSL 互证）。

## 9. 还能往上游回馈什么

- **仓颉缺 AES**：`stdx.crypto` 只有 SM4，且本机 SM4-GCM 不可用。我们的纯仓颉 AES-128-GCM 可以作为
  参考实现提交（配 NIST 向量测试）。
- **`stdx.net.http` 的 DELETE 带体**：能编译、能发，但 `HttpRequestBuilder` 只暴露 `get/post/delete`，
  文档里没写"DELETE 能否带 body / 会不会自动带 Content-Length"——这是这次靠试才定下来的。
- **`hdc` 退出码恒 0**：这是华为侧设计，值得在工具链文档里显式写"只能按文本判"。
