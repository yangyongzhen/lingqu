# P3 出口判据 1 · 验证方案（等 P5 跑通即执行）

> **判据原文**（`docs/实施路线图.md` P3）：*4 个本地样本上产出"不可用 crate 清单"，
> 与实际交叉编译失败点**吻合 ≥ 80%**（差异逐条解释）*。
>
> 本方案把"吻合"定义成可计算的口径、把执行固化成步骤与对照表模板——P5 的交叉编译
> 一跑通（T5-1），照 §3 八步直接执行，不需要再讨论"怎么算"。
>
> **为什么必须等 P5**：这一条没法在单测里做（D-009——进程/交叉编译不造假绿）。
> 它检验的是依赖矩阵的**预测力**，证据只能来自真实 `cargo build --target aarch64-unknown-linux-ohos`。

---

## 1. 要检验的对象与假设

被检验方：`lingqu-cli deps`（`lingqu.deps`）产出的依赖矩阵，判定三值域：

| 判定 | 含义 | 预测 |
|---|---|---|
| 需 patch | tauri 系/wry/tao/ability（R2-DEPS-001~004） | **未落 patch 时必然失败**；已落 patch → 预测可用 |
| 不可用 | openssl-sys/native-tls/rfd（R2-DEPS-010/011） | 直接失败（或运行期不可用——本判据只对编译期计） |
| 有条件可用 | reqwest（需 rustls）/dirs 等（R2-DEPS-020/021） | 条件不满足 → 预测失败；满足 → 预测通过 |
| 可用（默认直编） | 表外 615+ crate（R2-DEPS-000） | 预测通过 |

**被检验的假设（可证伪）**：规则库接得住"真会失败"的依赖，且不大量冤枉"能编过"的依赖。
其中最危险的是**假阴性（判可用但真失败）**——它会让 agent 按矩阵继续走，把用户带进沟里。

---

## 2. 口径定义（先钉死，防止算出"好看的 80%"）

### 2.1 失败点的归类

把一段交叉编译日志里的每个**根因失败点**归到三类之一：

| 类别 | 识别特征（日志原文） | 是否进 crate 吻合率 |
|---|---|---|
| **crate 级失败** | `error[E0432]: unresolved import`、`cannot find crate X`、`failed to select a version`、openssl 的 C 编译失败 | ✅ 进 |
| **工程配置失败** | feature 组合错（reqwest default 拉 native-tls）、`crate-type` 缺 cdylib、tauri.conf 问题 | ✅ 进（映射到触发它的 crate/规则） |
| **环境/工具链失败** | `-lgcc_eh`、`linker` not found、NDK clang、sysroot——**与 crate 无关** | ❌ 不进分母，单独统计（修工具链后重跑） |

`lingqu-cli diagnose --logPath <日志>` 已内置这批指纹（FP-001~015），归类可直接复用其输出；
diagnose 未命中的按上表人工归类，并**同步进 `misses.jsonl`**（这正是飞轮的证据层）。

### 2.2 混淆矩阵与公式（对 4 个样本的全部 crate 级失败点）

对每个样本：矩阵判定（预测）× 交叉编译结果（实际），得到四格：

| | 实际失败 | 实际编过 |
|---|---|---|
| 矩阵判**会失败**（不可用 / 需patch 未落 / 条件不满足） | **TP** | **FP**（误报） |
| 矩阵判**通过**（可用 / 需patch 已落 / 条件满足） | **FN**（假阴性，最危险） | TN |

- **主判据：召回率 Recall = TP / (TP + FN) ≥ 80%**——判据原文的"清单与实际失败点吻合"
  取这个方向：真会失败的地方，清单要接得住；
- **辅助指标：精确率 Precision = TP / (TP + FP)**——不设线但必须随报告给出：大量误报会把
  可迁的工程吓成"不可迁"，与"开辟低成本入鸿通道"的课题目标相悖（精确率 <60% 时即使
  recall 达标也要逐条解释 FP）；
- **每样本零失败的处理**：某样本交叉编译一把过（如干净的 juCang 可能如此）→ 该样本
  **不进分母**（0 失败无从对照），在报告里标注"零失败样本，矩阵未触发"，并记下矩阵里
  判"会失败"的条目数量（它们是潜在 FP 候选）；
- **工具链失败的处理**：先修环境再统计（否则 `-lgcc_eh` 这种环境错会稀释 crate 级口径）；
  修环境的过程本身验证的是 R2-PORT-007/008 规则，单独记。

### 2.3 差异逐条解释（判据原文的硬要求）

每个 FN 与 FP 各写一行：**现象 → 归因 → 处置**。归因只能落三类之一：

1. **规则缺**——依赖树里没见过的新失败模式 → 按经验入库规则提新指纹（FP-021…），
   若可规则化则同步提 R2-DEPS 规则；
2. **规则错**——evidence 与实际不符（如某 crate 实际可编但被表判不可用）→ 修规则表并注明
   修正依据（哪个样本哪条日志）；
3. **样本特有**——该工程的私有代码问题，不该进通用库 → 只在样本报告里记，不回填规则库。

**循环上限**：每轮修复后重跑对照；最多 3 轮——3 轮后仍 <80% 说明规则库的覆盖策略有
结构性问题，升级为设计复盘（不无限烧轮次）。

## 3. 执行步骤（P5 跑通后照做）

**前置**：P5 T5-1 可用（`lingqu-cli build --path <工程>` 能产出完整交叉编译 stderr 日志）；
样本与矩阵落档齐（`deps` 已对 4 样本各跑一次，`.lingqu/deps/<工程>.json` 存在）。

1. **选样本**（判据原文"4 个本地样本"，名单与理由）：

   | 样本 | 选它的理由 | 预期 |
   |---|---|---|
   | habit-tree | 已真机成功的基线：矩阵判"需patch"的都应已落 patch → 理想情况零失败 | 零失败样本（对照 patch 有效性） |
   | m3u8dl-tauri | 媒体/子进程型，依赖形态不同（可能撞 FN——最有价值的发现源） | 少量失败 |
   | juCang | 干净未迁移工程：`port` 之前的原始依赖树 | 可能零失败，验证"不误报" |
   | atomMqtt（或 tauri-mqtt-client-ohos） | 网络长连接 + `wry-patched/` 特例 | reqwest/TLS 相关 TP 候选 |

   （替换规则：任一样本编不过且根因是样本自身损坏，可换成 mark_note / cc-switch，报告注明。）

2. **跑交叉编译**：对每个样本 `lingqu-cli build --path <工程>`，完整日志存
   `.lingqu/build/<工程>.log`（含退出码）；失败样本不修——**先取证再修**。

3. **归类失败点**：每个样本 `lingqu-cli diagnose --logPath .lingqu/build/<工程>.log`，
   按 §2.1 三类归档；crate 级失败点映射到具体 crate 名（E0432 的 import 路径、
   `failed to select a version` 的包名）。

4. **拉矩阵预测**：`lingqu-cli deps --path <工程> --json` 的 items 数组按 §1 表折算成
   "预测失败集"（含需 patch 未落、条件不满足的展开——reqwest 看工程实际 features）。

5. **填对照表**（模板见 §4），合并 4 样本得总表。

6. **算指标**：Recall（主判据 ≥80%）、Precision（辅助）、F1；零失败样本单独标注。

7. **差异逐条解释**：每个 FN/FP 按归因三分法写一行，处置动作直接开工
   （新指纹 / 修规则表 / 仅样本记录）。

8. **出结论**：结果与对照表写进 `docs/进度记录.md` + `docs/需求追踪.md`（M2 状态翻转：
   `已实现已验证（部分口径）` → `已实现已验证`），差量按 §2.3 循环（≤3 轮）。

## 4. 对照表模板（每样本一份 + 总表）

```markdown
## 样本：<工程名>（矩阵条数 N / 其中预测失败 M / 实际失败 K）

| # | 失败 crate / 点 | 日志证据（log:行） | 矩阵判定 | 规则 id | 吻合？ | 归因（TP/FP/FN） | 处置 |
|---|---|---|---|---|---|---|---|
| 1 | openssl-sys（经 reqwest default） | log:37: error: failed to run custom build… | 不可用 | R2-DEPS-010 | ✅ TP | — | — |
| 2 | <新依赖 X> | log:88: error[E0432]… | 可用（默认） | R2-DEPS-000 | ❌ FN | 规则缺 | 提 FP-021 + 评估规则化 |

本样本：TP=_ FP=_ FN=_ → Recall=_%（累计口径）
```

汇总行固定格式（进进度记录与需求追踪）：

```
Recall = TP/(TP+FN) = _/_ = __%（主判据 ≥80% ✅/❌）
Precision = TP/(TP+FP) = _/_ = __%（辅助，<60% 需逐条解释）
零失败样本：_（矩阵预测失败 _ 条未触发）
工具链失败：_ 条（修环境重跑，不进 crate 口径）
差异解释：FN _ 条 / FP _ 条（逐条见上表"处置"列）
```

## 5. 已知风险与预案

| 风险 | 影响 | 预案 |
|---|---|---|
| 样本多数一把过，失败点太少（分母小） | 80% 在小样本上统计意义弱 | 优先用**未迁移原始工程**（juCang/atomMqtt 跑 port 前的树）；仍不足则明确报告"分母 N=K，判据在 K≥5 时才具统计意义" |
| FN 集中在子进程/文件系统类（m3u8dl 型） | 暴露规则库盲区 | 这正是判据的价值——按入库规则回填，不许"解释过去就算" |
| 需 patch 条目已全落 patch（habit-tree） | 无失败点可对 | 用 `t2h:revert` 回滚 patch 段跑一次"未迁移态"对照（样本自带 A/B 能力），验证后再恢复 |
| diagnose 指纹与 deps 规则口径不一致 | 归类打架 | 本方案以**日志原文**归类为准，diagnose 只是辅助工具；不一致本身按 FN/FP 流程修 |
| 误报（FP）吓退使用者 | 与课题目标相悖 | Precision 随报告强制给出；FP 的 evidence 必须当场修（规则表错就是错） |
