## D-012 脚本：bash 为准，bat 委托，弃用 ps1

**背景**：门禁脚本第一版是 `test.ps1`（Windows 专用）。一天之内在同一份脚本上连撞三个坑：

1. 无 BOM 的 `.ps1` 被 PowerShell 5.1 按 GBK 解码 → 中文注释撑坏字符串引号 → 报「数组索引表达式丢失或无效」
2. 原生命令 `2>&1` 把 stderr 变成 **ErrorRecord 对象**，在 `$ErrorActionPreference='Stop'` 下
   管道里一枚举就抛「无法转换成 SwitchParameter」——**报错文案与真因毫无关系**，为此绕了三四轮
3. `Set-Content -Encoding UTF8` 会给 `.cj` / `.toml` 加 BOM，而这些文件不该有 BOM

同时仓库要跨平台（Windows 现在、Linux 后续、鸿蒙 PC 更后），PS 只有 Windows 有。

**决策**
- **`scripts/*.sh` 是唯一实现**（Linux/macOS 原生，Windows 走 Git Bash —— 本工具链本来就要求它：
  cj-tauri 自己的 `pack-win.sh` / `test.sh` 也是 bash）
- `scripts/*.bat` 只做一件事：**找到 bash 再委托**，参数与退出码透传，**纯 ASCII**
- **不再新增 `.ps1`**；已有的三个（`test.ps1` / `run-dev.ps1` / `tools/vendor-cjh.ps1`）已删除
- 原生输出一律**走临时文件重定向**收集，不用管道捕获（避免上面第 2 条）
- 环境变量里可能是 Windows 形式路径（`D:\x`）→ 脚本内 `to_posix` 归一化，否则 MSYS 的 PATH 全部失效（exit 127）

**后果**
- Windows 上跑脚本需要 Git for Windows 的 bash（本机已有 `D:\Program Files\Git\bin\bash.exe`，
  `.bat` 会自己找；找不到时给一句明确的安装提示）
- Linux 侧脚本**尚未在 Linux 上执行过**——按约定留到 Linux 接续时验证（`docs/需求追踪.md` G10）

**取代关系**：D-010 里"`.ps1` 必须 UTF-8 BOM"仍然成立（若将来确要写 PowerShell），
但**首选是不要写**。

## D-001 迁移工具的外壳用 cj-tauri

**背景**：工具本身是个桌面 GUI（七步工作台 + Agent 面板），要选外壳。

**决策**：用 cj-tauri（仓颉 + 系统 WebView）。

**理由**
- 与「被迁移的对象」同构：工具自己就是一个"类 Tauri 应用"，迁移规则能在自身上先自测（吃自己的狗粮）。
- 已有鸿蒙 ArkWeb 真机闭环（建窗/装载/IPC/多窗口/菜单/剪贴板），工具本身能编到鸿蒙 PC——答辩时是活的范式样板。
- 产物几 MB、不带 Chromium，与课题"轻量 Rust + 系统 WebView"叙事一致。
- 否决 Electron（100MB 起、自我打脸）、否决官方 Tauri（会把"被迁移对象"的 OHOS fork 不确定性引入工具自身）、
  否决纯 Web（没有原生窗口/文件对话框/多窗口，工作台体验差，也丢掉"工具自己是仓颉应用"这个加分点）。

**后果**：必须吃下 cj-tauri 的工具链约束（`CANGJIE_STDX`、C 桥 DLL、WebView2Loader、工作目录=工程根），
这些已固化进 `scripts/run-dev.ps1` 与 `docs/开发环境.md`。

## D-002 cjh 以进程外 web 模式驱动

**背景**：AI 能力要接进来，cjh 是仓颉实现的 Coding Agent Harness（已有 14 工具 + 技能 + MCP + 插件 + 审批流 + web 模式）。

**决策**：`cjh web --port 8765 --bind 127.0.0.1` 作为独立进程；GUI 通过 REST + WS 驱动它。

**理由**
- cjh 是 executable 根包（仓颉限制：executable 根包不能被 import），进程内嵌为库不可行。
- 进程隔离：agent 崩溃不拖垮 UI；可单独升级 cjh。
- 复用 `examples/ai-chat` 已验证的托管实现，省掉一大块试错。

**后果**：多一个进程与一个端口；引擎缺失时应用必须能降级（见 D-003）。

## D-003 cjh 生命周期语义

**决策**（六条，写死在 `src/cjh_host.cj`）
1. **就绪判据只有一条**：`GET /api/health` 收到 200。
2. **复用优先**：端口上已有 cjh（可能是用户自己的）就复用，不抢、不杀、退出时不动。
3. **收尾归属**：只有本应用拉起的（`gCjhOwned=true`）才在退出时终止。
4. **拉起用 `launchHidden()`**：本应用是 GUI 子系统，`std.process.launch` 会让 Windows 给子进程配控制台黑窗口。
5. **只绑回环**：cjh web 默认绑 `0.0.0.0` 且默认不带鉴权 token，等于把"能跑 shell、能读写工作区、能调 LLM"的整套 API 摆到局域网上。
6. **拉起前先收掉自己上一只**：否则旧进程占着端口，新实例绑定失败，表象只是"10 秒后仍不通"。

**理由**：这六条每一条都对应一个真实失败面（用户实例被误杀 / 黑窗口 / API 暴露 / 换路径重试失败）。

**后果**：语义比"能起来就行"复杂，改动前必须读本节与本文件。

## D-004 二进制必须过 SHA256

**决策**：`vendor/cjh/win-x64/` 的 4 个文件（`cjh.exe` + 3 个运行时 DLL）逐个算 SHA256，
与源码内嵌常量比对；**不符就报错、不解包、不执行**。

**理由**：cjh 是能跑 shell、能读写工作区的 agent 引擎。来路不明的同名文件被静默执行是不可接受的。

**后果**：升级 cjh 必须同时改 `src/cjh_host.cj` 里的 4 个常量（`tools/vendor-cjh.ps1` 会重算 `SHA256SUMS`，
但源码常量要手动同步）。漏改的症状是启动时一行 `vendor SHA256 不符`。

## D-005 随包形态用已解包目录

**背景**：ai-chat 随包的是官方自包含 zip（首次运行解包到安装目录）。

**决策**：灵渠随包**已解包目录**（`vendor/cjh/win-x64/`），直接校验后使用；zip 只在
`LINGQU_CJH_BUNDLE` 显式指定时作为兜底路径。

**理由**
- 省掉每次部署的解包开销与一个失败面（bsdtar 依赖、解包完整性）。
- 开发期直接改 vendor 里的文件即可，调试路径更短。

**后果**：将来做单文件分发（把 cjh 内嵌进 exe）时，才需要把解包逻辑提到一等公民
（框架侧已有提案：`cj-tauri/docs/单文件包内嵌 cjh 方案.md`）。

## D-006 退出收尾用守护线程

**背景**：ai-chat 是旧形态 `main()` + `app.run(html)`，`run` 返回后调 `shutdownCjh()`。
灵渠用新形态 `AppSpec` + `launch(spec)`，业务拿不到"run 之后"那一行。

**决策**：`wire` 里 spawn 一条守护线程：先等主窗登记（wire 在 run 之前，此刻还没窗口，
不等会被 `allWindowsExited()` 误判成已退出）→ `app.waitForExit()` → `shutdownCjh()`，
且收尾跑 5 轮（200ms 间隔）。

**理由**：覆盖"用户秒关窗口 + 后台拉起还在途中"的抢跑；单次收尾有可能在 `gCjhOwned`
变 true 之前就跑完，等于没收。

**后果**：若框架将来提供 `AppSpec.onExit` 钩子，应改用钩子并删除守护线程。

## D-007 引擎自动拉起但放后台线程

**决策**：应用启动时自动 `ensureCjhWeb()`，但在 `spawn` 出来的后台线程里做。

**理由**：就绪等待最长 10s，放在主线程会推迟窗口出现（ai-chat 就是同步等的，代价是启动可能卡 10s）。
放后台线程后窗口立即出来，右栏状态从"待拉起"变"已就绪"。

**后果**：需要状态轮询（见 D-008）。退出时要处理"拉起在途"（见 D-006）。

## D-008 引擎状态用三态

**决策**：`t2h:cjh_status` 返回 `running` / `ready` / `missing`（外加端点或二进制路径）。

**理由**：`alive` 布尔分不清"没装"与"装了没起"，页面因此给不出正确的下一步
（该给"启动"还是"去部署"）。三态是让 UI 能给出**正确动作**的最小信息量。

**后果**：无。

## D-009 单测只测纯函数

**决策**：单元测试只覆盖纯函数（拼接、候选选择、端口解析、JSON 形状、校验失败路径）；
进程、网络、WebView2、真机部署**不在单测里模拟**，以实机为准并在 `docs/进度记录.md` 标注验证程度。

**理由**：把不可验证的东西"测绿"等于制造假证据。门禁的价值在于可信，不在于用例数量。

**后果**：验收项的证据要多一条来源（日志 / 截图 / 真机行为），不能只看 CI 绿。

## D-010 脚本编码纪律

**决策**
- `.ps1` **必须 UTF-8 带 BOM**：Windows PowerShell 5.1 读无 BOM 的 `.ps1` 按 ANSI(GBK) 解码，
  中文注释会把字符串引号撑坏，报「数组索引表达式丢失或无效」。
- `.bat` **必须纯 ASCII**：cmd.exe 按 OEM 代码页读，中文会破坏后续行解析（框架 `run_win.bat` 同款结论）。
- **禁止用 shell 做源码文本回写**（`Get-Content | Set-Content`）：PS 5.1 会按 GBK 误解码无 BOM 的 UTF-8，
  且 `Set-Content -Encoding UTF8` 会给 `.cj` 加上 BOM。

**理由**：三条都是实测踩出来的，且失败现象与真实原因相距很远（看着像语法错/编译器问题）。

**后果**：改源码用工具链的精确替换能力，改完 `git diff` 复核；脚本文件头已写明这条纪律。

## D-011 规则优先 + 证据化验收

**决策**
- 迁移改造"确定性优先、AI 兜底"：可枚举的机械改造走规则（零 token、可复现），LLM 只处理规则未命中的长尾。
- 任何验收结论必须能指到可复核证据（编译通过 / `.so` 指纹 / 真机无 panic / 截图），
  禁止"编译过了就算迁移成功"。

**理由**：这是本项目与"再写一个更长的脚本"、"纯 LLM 一把梭"两条路线的分界，也是评审最看重的方法论差异。

**后果**：验证器（`t2h:verify`）与证据链的优先级高于"功能数量"；写功能前先想清楚证据怎么取。

## D-012 脚本一律 bash 为准，`.bat` 只做委托，不再新增 `.ps1`

**决策**：功能实现只写 `scripts/*.sh`；`*.bat` 只负责「找到 Git Bash 再把参数原样转过去」；仓里不再新增 `.ps1`。

**理由**：`.ps1` 踩了三个坑（无 BOM 被按 GBK 解码、`2>&1` 把 native stderr 变成 ErrorRecord 后在
EAP=Stop 下炸且报错文案误导、`Set-Content` 给 `.cj`/`.toml` 加 BOM），且 Windows 专用实现不利于
后续 Linux 接续——而本项目最终要在鸿蒙/信创环境的 PC 上跑。

**后果**：Windows 上多一层「找 bash」的启动开销（可忽略）；`.bat` 必须纯 ASCII、`.sh` 必须 LF。

## D-013 静默失败零容忍：写盘/读盘失败必须进返回值

**决策**：凡是"结果要留档"的动作（扫描落盘、报告生成、证据采集），失败原因**必须进命令返回值**
（本项目的 `outError` 字段）并由界面显示；只打 `eprintln` 视为**没有做失败处理**。

**背景（真实事故）**：0.6.0 的 `t2h:scan` 从工程路径取末段只按 `/` 切，Windows 路径
`E:\test\rust\habit-tree` 整条被当名字 → 落档路径 `.lingqu/scan/E:\test\rust\habit-tree.json` 非法 →
`FSException: The input path 'parent' … does not exist`。异常被 `catch` 后只 `eprintln`，
而 GUI 下 stderr 被框架日志接管（AGENTS §4 第 14 条）——**整轮扫描证据静默丢了**，
界面还显示"扫描成功"。0.7.0 才被发现。

**理由**：GUI 应用没有终端，日志不是用户能看到的地方；"成功"与"写盘失败但分析成功"必须能被区分，
否则证据链从根上不可信（D-011 的前提）。

**后果**：命令返回值多一些诊断字段（`outError`），`ui_report` 也带上它；新增落盘动作时按此办理。

## D-014 C2 用「人工基线双向 diff」，且基线先于扫描器

**决策**

1. **C2 的唯一算法**：`C2 = (基线项 − 漏识别) ÷ 基线项`；漏识别 = 基线有、扫描没有。
   误识别（扫描有、基线没有）只计数不扣分；结论分歧只计数，用来盯判定表。
2. **基线入库**（`samples/baselines/<工程>.json`），带 `source` 字段写清"谁、什么时候、读了哪些文件"。
3. **基线先于扫描器**：先人工通读列清单、再跑扫描；发现漏识别后**补扫描规则**，绝不改基线来凑 100%。
4. **没有基线就不出 C2**（`-1`，界面显示"未对照"），不接受"用默认值 100%"。

**理由**：C1 = D/R 有天然漏洞——识别得越少越容易 100%，甚至"全标人工"也能 100%。
C2 是反方向校验，它必须建立在**独立产生的**人工判断上；一旦基线是照着扫描结果写的，
C2 就变成自证，这个指标就废了。

**边界（写死，避免基线无限膨胀）**：库依赖（`serde`/`chrono`/`redb`/`base64`/`std::fs`…）归 P3 依赖维，
不进基线；**死代码里的能力要进基线**（结论写 `不适用`），否则扫描器的"多识别"会被误判成误识别。

**后果**：新增样本要先花 0.5–1 小时人工通读；基线与扫描规则必须同批维护（改规则后要重跑 diff）。
实测价值：habit-tree 第一轮 **83.3%**（漏 4 项）→ 补规则后 **100%**，4 个漏项里有 1 个
（`getVersion`）催生了「前端 `@tauri-apps/api` 能力」这一整类解析。

## D-015 **方向的定盘星：cjh 是执行者，工具是它的手，人只在它主动要求时介入**

**决策**（写死，任何一轮改动都不得违背）

1. **执行者是 cjh**。迁移的分析、改码、重跑、判断"下一步做什么"，都由内置的 agent 干。
   它不是"失败后给建议的顾问"——那是把 agent 降级，方向就错了。
2. **工具是它的手**：`t2h:*` / `lingqu-cli` / `.lingqu/` 落档，都是给 agent 用的器官；
   我们的工作是**把器官递到它手上并保证能用**（绝对路径、技能、工程上下文、工作区、轮次预算）。
3. **人的位置**：只在 agent **主动要求**时介入（要人拍板的取舍、平台限制登记、真机操作）。
   设计上要**尽量少让人点**——"单应用人工介入 ≤5 处"是验收指标，不是体验指标。
4. **判据只认落档**：agent 说"迁好了"不算，`.lingqu/<步骤>/<工程>.json` 写着通过才算。
   我们看的是落档，不是它的自述。
5. **我们的三种角色**：眼睛（读落档做进度与停滞观测）、手刹（预算/停滞/一键停止）、
   记录员（人工介入次数 = A3 指标）。

**理由**：0.36.0 犯过这个错——把"一键迁移"做成**确定性流水线**：我们按固定顺序跑 8 个命令，
失败才问 AI 一次，建议还要人点。结果 AI 全程在边缘，工具在中心，正好与人机协作的方向相反。
用户当场纠正："这个项目里已经内置了 cjh，可以帮助干移植的活"。

**反例清单（看到就说明做反了）**

- 界面上做成"每一步一个人点按钮"的向导；
- 让用户（或文档）教人"手动跑 `lingqu-cli build` 再点下一步"；
- 把 AI 的输出只当"解释/建议"，动作仍由我们的代码或人执行；
- 失败时只把现场发给 AI 要一段建议，而不让它接着动手；
- 由我们替 agent 决定"这一步该怎么修"（那是抢它的活）。

**后果**：确定性流程保留但**降级**为兜底与工具（无 AI 时能跑、也是 agent 的手）；
主路径是 `t2h:autoport_*`（准备现场 → 交任务书 → 盯落档）。
0.37.0 实测教训：这条路真正的堵点是 **cjh 没有 REST 对话入口**（只有 `/ws`），
已作为上游缺口 #2 记录在 `docs/上游回馈-cjh.md` —— 修它属于"把器官递到它手上"，
优先级高于再写任何界面。

## D-016 断点板跟工程走：`<工程>/.lingqu/tasks.json`

**决策**

1. 8 步断点板落在 **`<工程>/.lingqu/tasks.json`**，与其它落档同一个 `.lingqu/`，工程自包含。
2. 位置**单点定义**在 `src/task_feed.cj` 的 `taskBoardPathFor(projectPath)`（内部走 `lqPathOf`）；
   任何调用方都不许自己拼字符串。
3. **读侧一律 `resolveLqPath(projPath, "tasks.json")`**：工程优先、CWD（旧应用级位置）兜底。
   迁移期旧板子照样读得到——切换落档路径绝不能把已有证据读丢。
4. 工程路径为空（CLI 没给 `--path`、老调用方）→ 退回旧的 `.lingqu/tasks.json`，行为不变。

**理由**：0.39.7 之前板子在**灵渠应用目录**，跨工程共用。症状很直观：`m3u8dl-tauri` 那轮跑完
再打开 `habit-tree`，顶部还写着上一个工程停在"真机部署"。这与"8 个路径框各填一遍"同源——
**同一件事实存了两份权威**（顶部「当前工程」是权威，落档却不知道自己在哪个工程里）。
一个路径类落档只要还挂在应用目录，就永远会串工程。

**代价与边界**

- 板子会写进**被测工程**的目录（与 scan/deps/port/build/hap/sign/deploy/verify 的落档一致），
  样本仓里会多 `.lingqu/`（已列入各样本的忽略项）。
- 迁移期双读带来的"旧板子可能被读到"是**有意保留**的：宁可读到旧进度，也不要在切换当天
  让所有人的断点凭空消失。等所有调用方都切完并实测一轮后，再删 `resolveLqPath` 的 CWD 兜底。

**证据**（0.39.8）：`lingqu-cli resume --path` 两个工程各回各的 `out`；
跑 `m3u8dl-tauri` 前后 `habit-tree` 的 `tasks.json` SHA256 不变。

**纪律**：这是"落档路径"改动，**产出方与消费方必须同一批改**（AGENTS §4-33）：
写侧 `saveTaskBoard`、读侧 `collectTaskBoard` / `ResumeCommand` / `ReportCommand` /
`report_feed` 的证据清单，以及注入给 agent 的文案，缺一处就静默破坏另一条链路。

## D-017 签名材料按**包名**签发：工具只做体检与"一次说清"，不替人猜

**决策**

1. **包名门槛是独立判定**：`SignCheck.bundleMatch` 单独存在，不塞进 `filesExist` 之类的开关。
   `profile` 由签名服务按 `bundle-name` 签发，工程 `AppScope/app.json5` 的 `bundleName` 与它不一致时，
   hvigor 在 `default@SignHap` 直接失败（`00303074`）。
2. **"候选材料 > 0" ≠ "能写回"**：候选数、文件齐全、含本机 UDID 三者都满足，仍可能因为包名不符而不可用。
   界面与落档必须分开表达（`candidateCount` / `filesExist` / `bundleMatch`）。
3. **不写会失败的配置**：`t2h:sign apply` 在包名不匹配时**拒绝写回**，并把正解写清。
   写进去只是把「材料缺失」换成「配置错误」，且人会误以为是口令/路径问题——比没配更难排查。
4. **正解只有一条人工路径**：在 DevEco 里对**该工程**点一次「Automatically generate signature」
   （需登录华为账号，把本机 UDID 注册进这个包名的 profile）。这属于**必须计入 A3 的人工介入**，
   工具做的是把它一次说清（缺哪个包名、本机有哪些包名、hvigor 报什么码、该点哪里）。
5. 新包名 = 新 profile；一个包名缺材料时，**不能**靠"借"别的包名的材料解决。

**理由**：0.39.7 把 `hap/sign` 的 `ok=false` 归因成"材料文件不存在"，据此给出的改法（换成现存那套）
在 0.39.9 被实测否掉：换完之后 hvigor 的报错从 `00303107 Invalid storeFile` 变成 `00303074
bundleName … does not match`——**照着建议做，仍然装不上**。给"会失败的建议"比不给建议更糟：
人会以为是自己操作错了，然后在口令与路径上反复试。

**代价**：5 个样本各自需要一次 DevEco 自动签名（每个新包名一次人工介入）。这是外部约束，
不是工具缺陷；把它写进 A3 台账比伪装成"能自动搞定"诚实。

**证据**（0.39.9，Windows x64）：
- 实验：m3u8dl-tauri（`com.atomgit.m3u8dl_tauri`）指向现存 probe 材料 + 同套材料的口令密文 → hvigor `00303074`；
  实验后工程文件按原样还原（SHA256 一致）。
- 实跑：`lingqu-cli sign` 的 `candidateBundleMatch=false` 与"缺哪个包名/本机有哪些包名"的 nextStep；
  `LINGQU_SIGN_APPLY=1` 时 `applied=false` 且工程文件未被改动。
- HAP 闸：`hapSignHint` 把 `00303074 / 00303107` 翻成闸门里的失败行。

## D-018 自动签名走「云生成材料」，但**私钥永不出本机**，且工具只在"同一套材料"上改配置

**决策**（路线 A 的边界，0.39.22 真机打通后定稿）

1. **只在本地生成密钥**：`hap-sign-tool generate-keypair` + `generate-csr`，`.p12` 从不离开本机；
   上云的只有 CSR 与包名/UDID。证书、profile 由 AGC 签发，下载到 `~/.ohos/config`（DevEco 同名规则）。
2. **证书按"有效期"挑，不按名字挑**：`auto_debug_<teamId>.cer` 名字对得上但可能早已过期，
   拿它申请 profile 会被回 `The certList is invalid.`。可用性判定收在 `AgcCert.usable()`。
3. **腾位置只删自己的**：AGC 证书有数量上限（实测 4 张），过期件照样占位。`staleCertsOf` 只挑
   「已过期 **且** 名字以 `auto_debug_`/`auto_release_` 开头」的，绝不替用户删他手工建的证书。
4. **配置写回分两种情形**：
   - `signingConfigs` 为空 → 注入新块（`injectSigningConfigs`）；
   - 已有内容**且 `storeFile` 就是我们要写的那份 `.p12`** → 就地更新（`replaceOwnSigningConfigs`），
     因为复用同一密钥时 `.p7b/.cer` 会随证书换发而变；
   - 已有内容但**是另一套材料** → 拒绝并说明（不静默覆盖别人的配置）。
5. **口令明文的边界**：拿到明文（自己生成的 p12）就用 `material/` 加密写回；拿不到（材料来自别处 /
   `material/` 重建过）**不猜**——此时提供 `--newKeys` 换一套自己掌口令的材料。判断"能不能用现有密文"
   的判据不是猜，而是 `--reencrypt` 能不能解开：解不开就是 `GCM tag mismatch`。

**理由**：0.39.22 实测把整条链跑到 `signed=true` 与 `install bundle successfully`，中途六个失败点全部
出在"名字对得上但语义不对"（同名过期证书、同名旧公钥、配置非空、密文解不开）。这些都不该靠人肉判断：
**同一个名字在不同时刻可能指向不同的东西**，判据要落在语义字段（有效期、公钥、材料身份）上。

**代价**：`material/` 重建或换机器后，旧 `.p12` 的口令永久丢失 → 必须重生成材料（也就意味着换证书，
消耗一次证书配额）。这是"不猜口令"换来的确定性，接受。

**证据**（0.39.22，HarmonyOS PC `3QC0124B20000048`）：
`sign --auto --newKeys` → `ok=true`；`hap` → `signed=true hapBytes=8,273,766`；
`deploy` → `install bundle successfully`；`--reencrypt` 对旧密文报 `GCM tag mismatch`（这就是"旧密文
不可用"的可判定证据）。
