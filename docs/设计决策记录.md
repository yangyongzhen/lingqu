## D-012 脚本：bash 为准，bat 委托，弃用 ps1

**背景**：门禁脚本第一版是 `test.ps1`（Windows 专用）。一天之内在同一份脚本上连撞三个坑：

1. 无 BOM 的 `.ps1` 被 PowerShell 5.1 按 GBK 解码 → 中文注释撑坏字符串引号 → 报「数组索引表达式丢失或无效」
2. 原生命令 `2>&1` 把 stderr 变成 **ErrorRecord 对象**，在 `$ErrorActionPreference='Stop'` 下
   管道里一枚举就抛「无法转换成 SwitchParameter」——**报错文案与真因毫无关系**，为此绕了三四轮
3. `Set-Content -Encoding UTF8` 会给 `.cj` / `.toml` 加 BOM，而这些文件不该有 BOM

同时仓库要跨平台（Windows 现在、Linux 后续、鸿蒙 PC 更后），PS 只有 Windows 有。

**决策**
- **`scripts/*.sh` 是唯一实现**（Linux/macOS 原生，Windows 走 Git Bash —— 本工具链本来就要求它：
  cj-tauri 自己的 `pack-win.sh` / `test.sh` 也是 bash）
- `scripts/*.bat` 只做一件事：**找到 bash 再委托**，参数与退出码透传，**纯 ASCII**
- **不再新增 `.ps1`**；已有的三个（`test.ps1` / `run-dev.ps1` / `tools/vendor-cjh.ps1`）已删除
- 原生输出一律**走临时文件重定向**收集，不用管道捕获（避免上面第 2 条）
- 环境变量里可能是 Windows 形式路径（`D:\x`）→ 脚本内 `to_posix` 归一化，否则 MSYS 的 PATH 全部失效（exit 127）

**后果**
- Windows 上跑脚本需要 Git for Windows 的 bash（本机已有 `D:\Program Files\Git\bin\bash.exe`，
  `.bat` 会自己找；找不到时给一句明确的安装提示）
- Linux 侧脚本**尚未在 Linux 上执行过**——按约定留到 Linux 接续时验证（`docs/需求追踪.md` G10）

**取代关系**：D-010 里"`.ps1` 必须 UTF-8 BOM"仍然成立（若将来确要写 PowerShell），
但**首选是不要写**。

## D-001 迁移工具的外壳用 cj-tauri

**背景**：工具本身是个桌面 GUI（七步工作台 + Agent 面板），要选外壳。

**决策**：用 cj-tauri（仓颉 + 系统 WebView）。

**理由**
- 与「被迁移的对象」同构：工具自己就是一个"类 Tauri 应用"，迁移规则能在自身上先自测（吃自己的狗粮）。
- 已有鸿蒙 ArkWeb 真机闭环（建窗/装载/IPC/多窗口/菜单/剪贴板），工具本身能编到鸿蒙 PC——答辩时是活的范式样板。
- 产物几 MB、不带 Chromium，与课题"轻量 Rust + 系统 WebView"叙事一致。
- 否决 Electron（100MB 起、自我打脸）、否决官方 Tauri（会把"被迁移对象"的 OHOS fork 不确定性引入工具自身）、
  否决纯 Web（没有原生窗口/文件对话框/多窗口，工作台体验差，也丢掉"工具自己是仓颉应用"这个加分点）。

**后果**：必须吃下 cj-tauri 的工具链约束（`CANGJIE_STDX`、C 桥 DLL、WebView2Loader、工作目录=工程根），
这些已固化进 `scripts/run-dev.ps1` 与 `docs/开发环境.md`。

## D-002 cjh 以进程外 web 模式驱动

**背景**：AI 能力要接进来，cjh 是仓颉实现的 Coding Agent Harness（已有 14 工具 + 技能 + MCP + 插件 + 审批流 + web 模式）。

**决策**：`cjh web --port 8765 --bind 127.0.0.1` 作为独立进程；GUI 通过 REST + WS 驱动它。

**理由**
- cjh 是 executable 根包（仓颉限制：executable 根包不能被 import），进程内嵌为库不可行。
- 进程隔离：agent 崩溃不拖垮 UI；可单独升级 cjh。
- 复用 `examples/ai-chat` 已验证的托管实现，省掉一大块试错。

**后果**：多一个进程与一个端口；引擎缺失时应用必须能降级（见 D-003）。

## D-003 cjh 生命周期语义

**决策**（六条，写死在 `src/cjh_host.cj`）
1. **就绪判据只有一条**：`GET /api/health` 收到 200。
2. **复用优先**：端口上已有 cjh（可能是用户自己的）就复用，不抢、不杀、退出时不动。
3. **收尾归属**：只有本应用拉起的（`gCjhOwned=true`）才在退出时终止。
4. **拉起用 `launchHidden()`**：本应用是 GUI 子系统，`std.process.launch` 会让 Windows 给子进程配控制台黑窗口。
5. **只绑回环**：cjh web 默认绑 `0.0.0.0` 且默认不带鉴权 token，等于把"能跑 shell、能读写工作区、能调 LLM"的整套 API 摆到局域网上。
6. **拉起前先收掉自己上一只**：否则旧进程占着端口，新实例绑定失败，表象只是"10 秒后仍不通"。

**理由**：这六条每一条都对应一个真实失败面（用户实例被误杀 / 黑窗口 / API 暴露 / 换路径重试失败）。

**后果**：语义比"能起来就行"复杂，改动前必须读本节与本文件。

## D-004 二进制必须过 SHA256

**决策**：`vendor/cjh/win-x64/` 的 4 个文件（`cjh.exe` + 3 个运行时 DLL）逐个算 SHA256，
与源码内嵌常量比对；**不符就报错、不解包、不执行**。

**理由**：cjh 是能跑 shell、能读写工作区的 agent 引擎。来路不明的同名文件被静默执行是不可接受的。

**后果**：升级 cjh 必须同时改 `src/cjh_host.cj` 里的 4 个常量（`tools/vendor-cjh.ps1` 会重算 `SHA256SUMS`，
但源码常量要手动同步）。漏改的症状是启动时一行 `vendor SHA256 不符`。

## D-005 随包形态用已解包目录

**背景**：ai-chat 随包的是官方自包含 zip（首次运行解包到安装目录）。

**决策**：灵渠随包**已解包目录**（`vendor/cjh/win-x64/`），直接校验后使用；zip 只在
`LINGQU_CJH_BUNDLE` 显式指定时作为兜底路径。

**理由**
- 省掉每次部署的解包开销与一个失败面（bsdtar 依赖、解包完整性）。
- 开发期直接改 vendor 里的文件即可，调试路径更短。

**后果**：将来做单文件分发（把 cjh 内嵌进 exe）时，才需要把解包逻辑提到一等公民
（框架侧已有提案：`cj-tauri/docs/单文件包内嵌 cjh 方案.md`）。

## D-006 退出收尾用守护线程

**背景**：ai-chat 是旧形态 `main()` + `app.run(html)`，`run` 返回后调 `shutdownCjh()`。
灵渠用新形态 `AppSpec` + `launch(spec)`，业务拿不到"run 之后"那一行。

**决策**：`wire` 里 spawn 一条守护线程：先等主窗登记（wire 在 run 之前，此刻还没窗口，
不等会被 `allWindowsExited()` 误判成已退出）→ `app.waitForExit()` → `shutdownCjh()`，
且收尾跑 5 轮（200ms 间隔）。

**理由**：覆盖"用户秒关窗口 + 后台拉起还在途中"的抢跑；单次收尾有可能在 `gCjhOwned`
变 true 之前就跑完，等于没收。

**后果**：若框架将来提供 `AppSpec.onExit` 钩子，应改用钩子并删除守护线程。

## D-007 引擎自动拉起但放后台线程

**决策**：应用启动时自动 `ensureCjhWeb()`，但在 `spawn` 出来的后台线程里做。

**理由**：就绪等待最长 10s，放在主线程会推迟窗口出现（ai-chat 就是同步等的，代价是启动可能卡 10s）。
放后台线程后窗口立即出来，右栏状态从"待拉起"变"已就绪"。

**后果**：需要状态轮询（见 D-008）。退出时要处理"拉起在途"（见 D-006）。

## D-008 引擎状态用三态

**决策**：`t2h:cjh_status` 返回 `running` / `ready` / `missing`（外加端点或二进制路径）。

**理由**：`alive` 布尔分不清"没装"与"装了没起"，页面因此给不出正确的下一步
（该给"启动"还是"去部署"）。三态是让 UI 能给出**正确动作**的最小信息量。

**后果**：无。

## D-009 单测只测纯函数

**决策**：单元测试只覆盖纯函数（拼接、候选选择、端口解析、JSON 形状、校验失败路径）；
进程、网络、WebView2、真机部署**不在单测里模拟**，以实机为准并在 `docs/进度记录.md` 标注验证程度。

**理由**：把不可验证的东西"测绿"等于制造假证据。门禁的价值在于可信，不在于用例数量。

**后果**：验收项的证据要多一条来源（日志 / 截图 / 真机行为），不能只看 CI 绿。

## D-010 脚本编码纪律

**决策**
- `.ps1` **必须 UTF-8 带 BOM**：Windows PowerShell 5.1 读无 BOM 的 `.ps1` 按 ANSI(GBK) 解码，
  中文注释会把字符串引号撑坏，报「数组索引表达式丢失或无效」。
- `.bat` **必须纯 ASCII**：cmd.exe 按 OEM 代码页读，中文会破坏后续行解析（框架 `run_win.bat` 同款结论）。
- **禁止用 shell 做源码文本回写**（`Get-Content | Set-Content`）：PS 5.1 会按 GBK 误解码无 BOM 的 UTF-8，
  且 `Set-Content -Encoding UTF8` 会给 `.cj` 加上 BOM。

**理由**：三条都是实测踩出来的，且失败现象与真实原因相距很远（看着像语法错/编译器问题）。

**后果**：改源码用工具链的精确替换能力，改完 `git diff` 复核；脚本文件头已写明这条纪律。

## D-011 规则优先 + 证据化验收

**决策**
- 迁移改造"确定性优先、AI 兜底"：可枚举的机械改造走规则（零 token、可复现），LLM 只处理规则未命中的长尾。
- 任何验收结论必须能指到可复核证据（编译通过 / `.so` 指纹 / 真机无 panic / 截图），
  禁止"编译过了就算迁移成功"。

**理由**：这是本项目与"再写一个更长的脚本"、"纯 LLM 一把梭"两条路线的分界，也是评审最看重的方法论差异。

**后果**：验证器（`t2h:verify`）与证据链的优先级高于"功能数量"；写功能前先想清楚证据怎么取。
