### 下一步（接手第一件事）：落档跟着工程走

**问题**：界面/命令跑出的落档在**灵渠应用目录**（`<lingqu>/.lingqu/`），agent 的 cwd 是
**目标工程**（`<project>/`）→ 它看不见落档；而我们注入的 AGENTS.md 却写"落在本工程的
`.lingqu/` 下"（**与事实不符**，agent 已实测指出：'`.lingqu/` 里只有任务书本身'）。

**方案（安全迁移，别一把梭）**

1. 新增 `src/workdir.cj`：`lqDirOf(projectPath)` → `<project>/.lingqu`；
   `lqPathOf(projectPath, rel)`；以及**读侧双查** `resolveLqPath(projectPath, rel)`：工程优先、CWD 兜底 ——
   这样旧落档不会失效，迁移可以一个命令一个命令来。
2. 先迁**产出者**：scan / deps / build / hap / sign / deploy / verify / report /
   batch / resume(tasks.json) / migrate(结果卡) 各自把 `.lingqu/...` 前缀换成
   `lqDirOf(projectPath)`。每迁一个命令跑一次门禁。
3. 再迁**消费者**：`observeTaskStep` / `taskArtifactPath` / 报告与矩阵的读路径统一走 `resolveLqPath`。
4. 最后改文案：`agentContextBody` 的落档表去掉"本工程"，改成准确的绝对路径；
   `buildAutoPortDirective` 里给出的 `.lingqu/<步骤>/<工程>.log` 也一并核对。
5. 单测：`lqDirOf`/`lqPathOf`（路径拼法、两种分隔符、空工程路径）+ `resolveLqPath` 的双查优先级。

**收益**：工程自包含（换机器/换会话都能自证）、agent 与界面看同一份落档、
`.lingqu` 可以随样本仓一起交付。

**这一轮改的是工具的态度**（不再是"照着做也失败的建议"）：

**本轮落地（全部离线、可自证）**

| 项 | 实现 | 怎么验证 |
|---|---|---|
| 材料命名 | `projectPathHash` / `signingFileBaseName` / `signingMaterialFileName` | 用 habit-tree 的工程根算出 `m7Gxh5QR…`，与磁盘上真实 `.p7b` 逐字一致；反斜杠路径算出 `EuNnZ1gj…`（反例） |

**关键环境发现（影响后续方案，必须先记下）**

- `stdx.crypto.crypto` 只提供 `OperationMode` / `PaddingMode` / `SecureRandom` / **SM4**——**没有 AES**；
  标准库 `std.crypto.cipher` 只有 `BlockCipher` 接口。
- `stdx.crypto.digest` 的 `HMAC` 可用（`HMAC(key) { => SHA256() }` 已编译通过）→ PBKDF2 能自己写。
- `stdx.net.http` 有 `ServerBuilder` / `HttpServer` / `TcpServer` → OAuth loopback 回调服务可行。

**因此路线 A 有两条实现路（下一轮的岔路）**

1. **自实现 AES-128 + GCM**（约 300 行）：可以用本机 .NET 的 `AesGcm` 生成权威测试向量对拍，

2. **复用本机已有 p12/cer + 口令密文，只向 AGC 申请新包名的 profile**：完全不碰 AES，
   更快通到 `signed=true`（缺点：复用的是同一套调试密钥，不是"全新材料"）。

## 已完成（2026-11-02，0.39.13）：口令密文打通（纯仓颉 AES-128-GCM + AesGcmKit 兼容）

**为什么这一步最关键**：写进 `build-profile.json5` 的 `storePassword`/`keyPassword` 是 hvigor 的
`AesGcmKit` 密文。算错一位，hvigor 只会报"签名失败"，不会告诉你 GCM/UTF-8/KDF 哪一步错了——
这是整条路线 A 里最容易**静默失败**的地方。

**走通的过程**

1. 查绝：仓颉 `std`/`stdx` 1.0.5.1 **没有 AES**（`stdx.crypto.crypto` 只有 `SM4`；
   `std.crypto.cipher` 只有 `BlockCipher` 接口）。而本机 **SM4-GCM 运行期直接抛**
   `CryptoException: Encrypt failed due to create tag error`（CBC/ECB/CTR 可用）→ 退路也没有。
2. 因此自实现：`src/compiler/aes_gcm.cj`（纯仓颉 AES-128-GCM，296 行）。
   **NIST SP 800-38D 的 TC1/TC2/TC4 向量**核对通过；期望值又用本机 Node/OpenSSL 独立复算了一遍。
   tag 篡改、换 key、载荷不足一律拒绝（常数时间比较）。
3. AesGcmKit 兼容层：`PBKDF2-HMAC-SHA256`（stdx 没有，自写；4 组公开向量核对）+
   `lossyUtf8Bytes`（非法 UTF-8 → U+FFFD，Node `toString('utf8')` 同语义）+ `material/` 读取 +
   口令加解密（载荷 `[len(4BE)|IV(12)|ct|tag(16)]` → hex）。
4. **决定性验证（两种独立实现互证）**

       仓颉：loadWorkKey(~/.ohos/config/material) + decryptPasswordHex(habit-tree 的 storePassword) → 通过
       Node（DevEco 自带 node / OpenSSL）独立复算：
         workKey = b730dc2388f8e70c645ac48fea7f22e4
         storePassword → "LtjnTDt7h8"（10 位字母数字，与 flutter 随机口令形态一致）
         keyPassword   → "LtjnTDt7h8"
       → 逐字节一致 ⇒ 我们**能自己生产 hvigor 解得开的口令密文**

**门禁**：`cjpm test` **310 例**（+8）；五道闸全绿、零警告。

**新发现的小坑（已进 AGENTS §4）**：`SecureRandom.nextBytes(buf)` 是**填缓冲区**，
不是"给长度返回数组"——知识库写成后者，照抄编译不过（`expected 'Array<UInt8>', found 'Int64'`）。

**下一步（路线 A 剩下的一半）**：OAuth loopback 登录 → 团队/设备 → 证书 → 按新包名申请 debug

## 已完成（2026-11-02，0.39.32）：工具执行秒表 + 「DOS 窗口闪」查清并记进上游

**用户实测**：「右侧 AI 聊天窗口信息不更新了，但屏幕上仍不时看到 dos 窗口一闪而过，像是还在执行，正常吗？」

**查下来是两件事**（都不算 bug，但界面没交代清楚）：

1. **聊天区不动**：cjh 回合是 `tool_start → 工具跑完 → tool_result`，工具执行期间**不发 delta**。
   我们只在 `tool_start` 插了张「执行中…」卡片，没秒表 → 长命令时像死机。
   现场佐证：引擎 5 秒内 CPU 只涨 0.09s（不是死循环），`~/.cjh/sessions` 无新堆积。
2. **DOS 窗口闪**：cjh 的持久 bash 会话用标准库 `launch` 起 shell（`bash_session.cj:158`），
   **无 `CREATE_NO_WINDOW`**；cjh 本身是我们用 `launchHidden` 拉起的（没控制台），
   于是 Windows 给每个 bash **新分配**控制台。实测进程链：`main.exe(cjh) → bash → bash → bash + conhost.exe`。

**处置**：
- 工具执行秒表：`tool_start` 起计时，卡片每秒刷 `执行中… Ns`，顶栏 AI 区显示 `⏳ bash · Ns`；
  `tool_result`/`done`/`error`/中断 一律收表（`finishTurn` 兜底）。
- `ui_report` 新增 `aiToolRunning / aiToolName / aiToolElapsed / aiBusyText`；新增探针 `LINGQU_UI_PROBE=toolrun`。
- 上游回馈：`docs/上游回馈-cjh.md` 第 8 条（现场链路 + 根因 + 复现 + 三条建议）。

**验证**（`LINGQU_UI_PROBE=toolrun`）：

    tool-run-busy   running=1  name=bash  elapsed=4s  toolCards=1  errorCount=0
    tool-run-idle   running=0  name=(空)  elapsed=0s  toolCards=1  errorCount=0
