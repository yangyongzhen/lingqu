## 0. 一句话定位

> **把「照文档手工改一个 Tauri 应用」变成「一条命令 + 一份带证据的迁移报告」**：
> 用**确定性规则引擎**吃掉可枚举的机械改造，用**LLM Agent + 三层证据闭环**吃掉不可枚举的语义修补，
> 用**真机可验证的产物**（可安装 HAP、可回归清单、可回溯 diff）作为唯一的"完成"判据。

三个关键词，按重要性排序：**证据驱动（Evidence-Driven）** > **确定性优先（Rules-First）** > **AI 编排（AI-Orchestrated）**。

## 1. 课题理解与问题定义

### 1.1 为什么这是一个"真问题"

Tauri 的价值主张是"前端任意 Web 技术 + Rust 原生后端 + 系统 WebView"，产物几 MB。但鸿蒙 PC（HarmonyOS 2in1/桌面形态）在三件事上与 Windows/macOS/Linux 完全不同：

1. **没有 WebView2**，只有 ArkWeb（ArkUI 组件宿主的 Chromium 内核），加载的是 `tauri://` 自定义 scheme；
2. **没有 `.exe`**，产物必须是 DevEco 工程壳 + 交叉编译的 `.so` + hvigor 打包出的 **HAP**；
3. **平台语义不同**：无 `HOME` 环境变量、应用沙箱路径、无原生 `confirm/prompt`、`localStorage` 在自定义 scheme 下不可用、无原生文件对话框/系统证书库。

于是"迁移"不是语言迁移，而是**四类断裂的同时重接**：

| 断裂面 | 桌面现状 | 鸿蒙 PC 现实 | 自动化难度 |
|---|---|---|---|
| **构建链** | `cargo tauri build` → `.exe`/`.msi` | `aarch64-unknown-linux-ohos` 目标 + OHOS NDK clang + `ohrs` + `hvigor assembleHap` → HAP | 低（几乎全可枚举） |
| **依赖/版本** | crates.io 上的 tauri 2.x | 需 patch 到社区 `feat/open-harmony` fork，钉精确版本，补 `napi-ohos` 桥 | 中（版本矩阵 + 冲突消解） |
| **运行时行为** | WebView2 全能力 | ArkWeb，自定义 scheme 下多能力缺失/有渲染缺陷 | **高**（语义差异，需探测） |
| **平台能力/分发** | 系统 API、安装包 | 沙箱路径、签名 profile、上架材料自查 | 中（部分必须人工） |

### 1.2 手工迁移的真实成本（来自本项目已有的实证样本）

以作者本人已完成的 4 个真实迁移为例（本地仓库与文档可查）：

| 样本 | 形态 | 规模 |
|---|---|---|
| `habit-tree`（习惯树） | Windows 桌面 → nova 14 真机 | **69 个文件变更（改 10 / 新增 59），+2383 / −228 行**，8 步流程，5 类坑 |
| `tauri-mqtt-client-ohos`（AtomMQTT） | Tauri v2 → 鸿蒙 PC/ARM64 | 交叉编译 + `wry` patch + 前端轮询改造，含 64KB 移植/交叉编译指南 |
| `m3u8dl-tauri` / `cc-switch-harmonyos` | 第三方应用二次移植 | 各一份完整移植实录 |

关键观察：**改动量集中在"模板化的 10 个文件"+"一次性的 45 个 DevEco 壳文件"**——这恰恰是最适合自动化的部分；而真正耗费人力的，是那 5~10 个"坑"（localStorage、confirm/prompt、`type=color` 渲染、`.so` 内嵌前端、签名切 release/debug）。

### 1.3 已有自动化覆盖到哪里、断在哪里

已有的 `port-to-ohos.ps1`（342 行）已验证"规则脚本"路线可行，覆盖 8 个阶段：环境检查 → 工具链安装 → 项目改造（Cargo.toml/toolchain/链接器/图标）→ `tauri ohos init` → 交叉编译 `.so` → 前端同步 → `ohpm` 依赖 → `hvigor` 打包 HAP。

它**明确写出了自己的边界**（脚本内注释）：

```text
[!] commands.rs 使用了 rfd/explorer 等平台相关 API，请按指南加 #[cfg(not(target_env = "ohos"))] 分支（脚本不自动改代码）
```

即：**脚本能做"加配置"，做不了"改代码"；能报错，不能诊断。** 这正是 AI 工具的切入点，也是本项目与"再写一个更长的脚本"的本质区别。

### 1.4 目标 / 非目标

**目标（Do）**

- G1 一条命令把一个 Tauri v2 项目推进到"可安装、可启动"的 HAP；
- G2 **先诊断后动手**：输出可迁移度评分 + 阻塞项清单 + 预估剩余人工步骤；
- G3 编译/运行期错误能**自动诊断-定位-修补-复验**，并有轮次上限与回滚；
- G4 前端 ArkWeb 兼容层（`localStorage`/`confirm`/`prompt`/下载/文件选择）**自动注入、业务代码零改动**；
- G5 全过程产出**可回溯证据**：diff、错误指纹、验证探针结果、真机截图；
- G6 迁移**幂等可重放**：重复执行不叠加改动，可一键 `revert` 回干净仓库。

**非目标（Don't）**

- N1 不做"通用代码翻译器"（不把 Rust 业务逻辑改写成 ArkTS——那是另一个课题，且违背 Tauri 的架构优势）；
- N2 不承诺无人值守交付：**签名、SDK 版本对齐、上架材料**必须人参与，工具只做"检测 + 指引 + 预填"；
- N3 不试图修复 ArkWeb 自身的渲染缺陷（如 `type=color` 合成层问题），而是**检测 → 走降级路径 → 写入已知限制库**；
- N4 不重写 Tauri 上游 OHOS 支持（复用社区 fork，把版本矩阵与补丁管理做成配置）。

## 3. 设计原则

| # | 原则 | 工程含义 |
|---|---|---|
| P1 | **迁移 = 可验证的重建，不是翻译** | 每个动作都绑定一个 verify 探针；没有探针的动作不进流水线 |
| P2 | **确定性优先，LLM 兜底**（"能用规则别用模型"） | 规则命中率高的路径零 token、零不确定性；LLM 只处理规则未命中的长尾 |
| P3 | **证据闸门（Evidence Gate）** | 任何"修复"必须由下一层证据确认（编译 → 产物 → 运行时），否则标记 `unverified` 而不是 `fixed` |
| P4 | **幂等 + 可回滚** | 所有改动以"带标记的补丁集"表达（沿用现有 `# === OHOS port (port-to-ohos.ps1) ===` 思路），可重放、可撤销 |
| P5 | **人力定格（Auto / Assist / Guide）** | 三档动作分级，AI 不越界：Auto = 直接改；Assist = 出补丁待人确认；Guide = 只给步骤与命令 |
| P6 | **宿主的真实性** | 不模拟、不假设：ArkWeb 行为以真机/模拟器实测为准，探测结果进本项目自己的"能力矩阵"，而不是照抄网页知识 |

### 一次迁移的 7 个阶段（数据流）

```text
① doctor   环境体检        →  环境能力位图（缺什么、怎么补）
② scan     静态分析        →  migration.json（迁移 IR）+ 可迁移度评分
③ plan     计划生成        →  有序动作清单（Auto/Assist/Guide 分级）+ 阻塞项
④ port     执行改造        →  补丁集 + 兼容层注入（规则为主，Agent 补长尾）
⑤ build    构建打包        →  .so / HAP / 构建日志（结构化诊断）
⑥ verify   三层验证        →  证据链（构建证据/产物指纹/运行时探针/截图）
⑦ report   报告与回滚      →  HTML/MD 报告 + `lingqu revert`
             ↑___________________│ Agent 在这里介入（仅 ⑤⑥ 失败时）
```

## 5. 核心技术设计（重点章节）

### 5.1 项目模型与迁移 IR（M1 Scanner）

**目标**：把"读代码猜怎么改"变成"**先算清楚，再动手**"。

采集面（每项都产出结构化数据，不靠字符串匹配）：

| 采集项 | 来源 | 用途 |
|---|---|---|
| 包/依赖图 | `cargo metadata --format-version 1` | 判定 tauri/wry/tao 版本、识别需 patch 的依赖、计算可编译性 |
| Tauri 配置 | `src-tauri/tauri.conf.json` | `frontendDist`、`withGlobalTauri`、`assetProtocol`、`custom-protocol` 缺省 |
| 能力/权限 | `capabilities/*.json` | 生成 OHOS 侧 `capabilities/default.json`，校验前端实际用到的 API 有授权 |
| 前端 import 图 | `oxc`/`swc` 解析 + 打包产物 `dist/` | 定位 `localStorage`/`confirm`/`prompt`/`Blob` 下载/`<input type=file>`/`Notification` 的真实使用点 |
| 平台 API 使用面 | `syn` 解析 Rust AST | 找 `rfd`、`dirs`、`app_data_dir()`、`Command::new("explorer")`、硬编码路径 |
| 插件清单 | `Cargo.toml` features + 前端 `@tauri-apps/plugin-*` | 判定插件在 OHOS 是否可用，不可用则给降级方案 |
| 前端产物指纹 | `dist/` 文件名 hash | 后续用于校验 `.so` 是否嵌入了最新前端（见 5.4） |

**迁移 IR（`migration.json`）核心字段**（也是人机协作的契约）：

```jsonc
{
  "schema": "lingqu/v1",
  "project": { "root": "...", "tauri_version": "2.11.5", "frontend": "vite+ts", "bundle_id": "com.x.y" },
  "score": { "total": 78, "dimensions": { "build_chain": 90, "deps": 70, "runtime": 60, "platform_api": 75, "dist": 85 } },
  "blockers": [
    { "id": "B-03", "severity": "hard", "kind": "platform_api",
      "where": "src-tauri/src/commands.rs:112", "evidence": "rfd::FileDialog",
      "rule": "R3-004", "action": "assist", "eta": "5min" }
  ],
  "capabilities_probe": { "localStorage": false, "js_confirm": false, "color_picker": false }, // 留空=待实测
  "plan": [ { "step": 1, "op": "R1-001", "mode": "auto" }, { "step": 2, "op": "R5-002", "mode": "auto" } ]
}
```

**可迁移度评分**：不是营销数字，而是**加权阻塞项反推**——`hard` 阻塞一项封顶扣 20 分，`soft` 扣 5 分；评分直接映射到"预计还需多少人时"。评分的意义在于**给用户决策**：先迁哪个应用、哪些应用该放弃/降级。

### 5.2 规则引擎（M3 · 确定性改造）

**规则 = 四元组**：`when`（匹配） → `transform`（变换） → `verify`（探针） → `evidence`（出处）。

设计要点：

- **AST/结构化变换优先**：Cargo.toml 用 `toml_edit`（保注释与格式）、JSON5 用解析器、Rust 用 `syn`、TS 用 `oxc`；纯文本正则仅用于生成新文件；
- **标记化幂等**：所有注入以 `# === lingqu: rule-id ===` 包裹，重跑只更新不叠加；
- **规则带来源**：`evidence` 字段指向真实 commit / 文章 / 报错记录，可审计、可过期提醒。

**示例规则（真实、已实证有效）**

```yaml
# R2-001 依赖切 fork 并钉精确版本
id: R2-001
title: tauri 全家桶切 OHOS fork，并钉精确版本（^ 会绕过 patch）
when:
  file: src-tauri/Cargo.toml
  assert: deps.tauri matches "^2"
transform:
  op: cargo-patch
  pin: { tauri: "=2.11.5", wry: "=0.56.0" }
  source: { git: "{{kb.fork.url}}", branch: "feat/open-harmony", rev: "{{kb.fork.rev}}" }
  also_patch: [ tao, tauri-build, openharmony-ability@feat/0.3.0 ]
verify:
  - cmd: cargo metadata --format-version 1
  - assert: packages[?name=='tauri'].source =~ "feat/open-harmony"
evidence: habit-tree@2d447ec · PORTING_GUIDE §四「为什么钉 =2.11.5」
```

```yaml
# R3-004 平台相关依赖分段，避免 OHOS 编译失败
id: R3-004
title: 把 rfd（原生对话框）从通用依赖移到桌面平台段
when: { file: src-tauri/Cargo.toml, assert: deps.rfd exists }
transform:
  op: cargo-move-dep
  from: "[dependencies]"
  to:   "[target.'cfg(not(target_env = \"ohos\"))'.dependencies]"
  add_sibling:
    "[target.'cfg(target_env = \"ohos\")'.dependencies]":
      napi-derive-ohos: "1.1"
      napi-ohos: { version: "1.1", features: ["napi8"] }
verify: [ "cargo check --target aarch64-unknown-linux-ohos" ]
evidence: port-to-ohos.ps1 §3.3 · habit-tree「坑：OHOS 下 rfd 编译失败」
```

**规则包分类（初版 6 包，目标 60~80 条）**

| 包 | 内容 | 条数（初估） |
|---|---|---|
| R1 构建链 | toolchain、`.cargo/config.toml` 链接器包装、`ohos-clang` 包装、NDK/sysroot | 8 |
| R2 依赖/版本 | fork patch、版本钉、`crate-type` 补 `cdylib`、feature 补 `custom-protocol`/`protocol-asset`、napi 桥 | 12 |
| R3 平台 API | `rfd`/`dirs`/`HOME`/`app_data_dir` → 沙箱路径 + `cfg` 分支；panic hook 落盘 | 15 |
| R4 配置/权限 | `tauri.conf.json`（`withGlobalTauri`/`assetProtocol`）、`capabilities/default.json` | 6 |
| R5 前端兼容层 | localStorage 透明桥、confirm/prompt polyfill、下载桥、file input 降级、`type=color` 降级 | 10 |
| R6 打包/分发 | 图标 RGBA 化、`bundleName`、`compatibleSdkVersion` 对齐真机 API、签名 profile 切换、rawfile/`.so` 一致性校验 | 10 |

### 5.3 前端 ArkWeb 兼容层（M4 · 最高杠杆的一块）

这是**投入产出比最高的模块**：一次做好，所有迁移的应用都受益，而且能做到"业务代码零改动"。

**能力探测矩阵**（初版，实测数据来自已有样本；空项待实测补齐）

| 能力 | ArkWeb 实测 | 探测方式 | 自动降级方案 |
|---|---|---|---|
| `window.localStorage` | **不可用（null）**——`tauri://` 非标准 origin | 运行期 `typeof localStorage` | **透明桥**：内存 Map + 防抖写回 → `invoke` → Rust 侧 redb 表（API 完全兼容、跨重启持久、业务零改动） |
| `confirm` / `prompt` | **未接回调**：confirm 静默 `false`、prompt 返回 `null` | 探测返回值 | 应用内 Promise 化对话框（含配套 CSS，沿用现有设计令牌） |
| `<input type="color">` | **不支持**，且 `display:none` 仍参与合成层 → 导致整块 dialog 绘制丢失 | 特性探测 | 应用内色板 + hex 输入；**必须 `remove()` 元素**而非隐藏 |
| `Blob` 下载 / `a[download]` | 未接线（可能无动作） | 触发 + 观察 | Rust 端写文件 + 系统保存能力；或写入相册（TSFN 回传） |
| `<input type="file">` | 待实测 | 触发 file picker | 原生文件选择器桥 |
| `Notification` | 需权限 | `Notification.permission` | 权限降级 + 可选开关 |

**注入策略（按侵入性从低到高，由 Scanner 决定）**

1. 打包成独立包 `@lingqu/arkweb-shim`，前端 `import` 一行（推荐给可改源码的项目）；
2. `index.html` 内联 polyfill（在 module script 之前，零构建改动）——`habit-tree` 实测有效；
3. 由 Tauri 侧在 **document-start 注入**（对 `dist/` 已定型的项目，零源码改动）。

**关键设计约束**：兼容层必须**桌面端空转**（探测到原生可用则不安装），保证"迁移不回归桌面"。

### 5.4 证据采集与自动验证（M6 Verifier · 本项目的护城河）

**三层证据，逐层收紧**：

| 层 | 证据源 | 采集方式 | 通过判据 |
|---|---|---|---|
| **静态** | `migration.json`、AST | 自研 scanner | 阻塞项清零；规则覆盖率 ≥ 阈值 |
| **构建** | `cargo` JSON 诊断、`hvigor` 日志、`ohpm` 输出 | `cargo build --message-format=json` + 日志解析器 | error 数 = 0；警告分类入库 |
| **产物** | `.so`、HAP | `.so` 内 **AssetKey 明文 grep**；HAP 用 `zipfile` 查 `rawfile`/`libs`；`bm dump` 查版本号 | 前端指纹 = 最新 `dist/`；版本号 = 期望值 |
| **运行时** | hilog、ArkWeb console、截图、`panic.log` | `hdc shell hilog`、ArkWeb CDP、像素 diff、`uitest` dump | 无 panic / 无红色诊断条 / 关键像素在 / 关键文本在 |

三条**已验证有效的"指纹探针"**（直接来自踩坑记录，是本项目最硬的差异化细节）：

```text
① .so 是否嵌入了最新前端？
   grep .so 里的 vite 产物文件名（AssetKey 为明文）：ui-<hash>.js / index-<hash>.js
   → 新文件名在 = 嵌入最新 dist；旧文件名在 = .so 是旧的
② HAP 里是否还有死资源 rawfile？（tauri 运行时只读 .so 内嵌资源，rawfile 不被读取）
   python -c "import zipfile,sys;print(any('rawfile' in n for n in zipfile.ZipFile(sys.argv[1]).namelist()))" app.hap
③ 真机显示的版本号 = .so 内嵌 dist 的版本 → 版本号没变 = 前端没进 .so
```

> **根因级认知**（不少团队会踩且很难自证）：`tauri-codegen::EmbeddedAssets` 对**所有 target** 生效，把 `frontendDist` 编进 `.so`，运行时从 `.so` 读资源；`rawfile` 目录是**死资源**。所以「改前端 → 同步 rawfile → 重打 HAP」是**无效链路**，必须重编 `.so`。工具必须把这条做成**强校验 + 明确报错**，而不是让用户靠"真机还是旧界面"去猜。

**ArkWeb 前端可观测性（自研小工具，成本低价值高）**：给 OHOS 宿主壳加一个 dev-only 的 console 转发（ArkWeb `onConsole` → hilog 带 `[WEB]` 前缀），Verifier 侧按前缀抓取 → 前端报错、`TypeError`、红色诊断条都能变成结构化证据。这一点把"前端黑盒"变成"可断言"。

### 5.5 Agent 诊断-修复闭环（M7）

**只做一件事**：把"构建/运行失败的证据"变成"下一个可验证的动作"。不做自由重构。

```python
def repair_loop(project, budget=8):
    for round in range(budget):
        ev = verifier.collect()                 # 结构化证据：错误码/指纹/位置
        if ev.all_green():
            return Report(status="verified", evidence=ev)

        fp = fingerprint(ev)                     # 归一化错误指纹（去路径/去时间/去 hash）
        hits = kb.search(fp, top_k=3)            # ① 知识库命中（历史踩坑 + 规则）
        if hits:
            patch = kb.materialize(hits[0])      # 模板化补丁：确定性、可审计
            origin = "kb"
        else:
            ctx = context.build(ev, project)     # ② 未命中：给模型最小必要上下文
            cands = llm.propose(ctx, n=3, schema=PatchSchema)   # 强制结构化输出
            patch = select(cands, by="最小改动+可验证性")        # ③ 自检排序，不是盲选
            origin = "llm"

        apply(patch, scope=whitelist)            # 白名单文件；一次只改一处
        if not verifier.regress_guard():         # 桌面三平台不回归
            revert(patch); continue
        # 下一轮由构建证据来判定 → 回到循环顶部
    return Report(status="needs_human", blockers=ev.unresolved)
```

**安全边界（反幻觉的六道闸）**

| 闸 | 规则 |
|---|---|
| 文件白名单 | 只允许改 `src-tauri/{Cargo.toml,src/**,tauri.conf.json,capabilities/**}`、`src/**`、`index.html`；禁止碰 `.git`、`target/`、`gen/ohos/` 之外的一切 |
| 单点原则 | 每次只允许一处语义修改，避免"顺手重构"掩盖因果 |
| 结构约束 | 补丁必须是 AST/锚点级（`syn`/`oxc`/`toml_edit`），拒绝整体重写文件 |
| 编译闸 | 任何补丁未通过 `cargo check --target aarch64-…-ohos` 视为无效 |
| 回归闸 | 桌面目标（Windows/Linux）构建必须仍通过 |
| 轮次与经济性 | 上限 8 轮；同指纹失败 2 次即转 `Guide`（人来看），不再烧 token |

**为什么"指纹 → 模板"这一步是关键**：本项目已有 4 个真实迁移 + 约 270KB 的踩坑文档，可提炼出**几十条报错指纹 → 修复模板**的映射（如 `cannot find crate napi_ohos` → 补 napi 依赖；`linker x86_64-w64-mingw32-clang not found` → 装 llvm-mingw；`app_data_dir` panic → 沙箱路径 + `cfg` 分支）。**这些命中时不调用模型**——更快、更准、可审计，也是与"纯 LLM 一把梭"方案拉开差距的地方。

### 5.6 构建与打包流水线（M5）

要点（均为已实证的工程细节，不是设想）：

| 主题 | 处理 |
|---|---|
| Windows 工具链 | **必须** `stable-x86_64-pc-windows-gnullvm`（默认 GNU 工具链在 llvm-mingw 下缺 `-lgcc_eh`）；且 gnullvm 只装 Rust 组件，**不含 C 编译器**，需外挂 `llvm-mingw`（提供 `x86_64-w64-mingw32-clang`） |
| 链接器包装 | NDK 自带 clang 包装是 Unix shell 脚本，Windows 跑不了 → 生成 `ohos-clang.cmd`（`-target … --sysroot=… -D__MUSL__ -fuse-ld=lld`） |
| Rust 目标 | `aarch64-unknown-linux-ohos`（鸿蒙 PC/平板 ARM）/ `x86_64-unknown-linux-ohos` |
| 产物形态 | `[lib] crate-type` 必须含 `cdylib` → 产出 `lib<name>.so` |
| HAP 装配 | `cargo tauri ohos build` 在 Windows 上**装配步骤会失败属预期**（`.so` 已生成）→ 转 `hvigorw assembleHap` 手工装配 |
| 前端一致性 | 前端改动后**必须重编 `.so`**（渲染期从 `.so` 读资源）→ 工具把"改前端"与"重编 `.so`"绑定为一个不可分割的构建单元 |
| 签名两态 | 真机调试用 debugKey（`signingConfig: release → default`，debug profile 含设备 UDID）；上架切回 release。工具自动切换并**在上架前强提醒** |
| 安装路径坑 | `hdc file send <相对路径>` 会保留目录结构导致 `bm install` 报 `install file path invalid` → 工具统一 `cd` 到 HAP 目录再 send |
| SDK 对齐 | `compatibleSdkVersion` 必须 ≤ 真机 API（`hdc shell param get const.ohos.apiversion` 读取后自动改写） |

### 5.7 批量与回归（M10 · 支撑评测）

- 输入：一批 Tauri 仓库（本地 4 个 + 公开样本）
- 输出：矩阵表格（每仓：评分 / 自动修复轮数 / 人工干预项 / 构建时长 / 真机通过 / 桌面不回归）
- 用途：既是**评测引擎**，也是**规则库自我进化的数据源**（把新踩的坑自动回灌 KB）

## 7. 鸿蒙 PC 特化（区别于"迁到手机"）

课题明确是**鸿蒙 PC**，与手机形态的差异必须显式建模（下列标 ⚠ 者需在实现期实测校准）：

| 维度 | 手机（已有样本） | 鸿蒙 PC（本课题重点） | 工具动作 |
|---|---|---|---|
| 设备类型声明 | `phone` / `tablet` | **`2in1`**（桌面形态）⚠ | 规则自动补 `deviceTypes`，并校验与分发配置一致 |
| 窗口 | 单窗口、全屏 | 多窗口、可缩放、最小尺寸约束⚠ | 检测前端是否有固定视口假设；给 `window` 最小宽高建议 |
| 输入 | 触摸、软键盘 | 键鼠、快捷键、hover、右键菜单⚠ | 检测 `ontouchstart`-only 交互；补 hover/focus 与快捷键 |
| 取色/对话框 | 无原生 → 应用内实现 | 桌面语义期待原生观感 | 复用 ArkWeb shim，但保留桌面风格权衡 |
| 光标/DPI/多屏 | 少见 | HiDPI、多显示器⚠ | 截图基线按 DPI 分档；布局回归按缩放比 |
| 分发 | AppGallery 手机通道 | PC 通道 + 平板/PC 互通自查 | 报告内置上架自查清单 |

> 说明：手机上验证过的结论（如 `localStorage` 不可用）在 PC 上**大概率一致但不保证**，因此 5.1 的 `capabilities_probe` 字段设计为"留空=待实测"，由 Verifier 在目标设备上实测回填。**这是本项目与"抄文档"型工具的分界：能力矩阵是自己测出来的。**

## 8. 知识库设计（M8）

三类知识，统一 schema，**每条都有证据链**：

| 类 | 结构 | 来源 | 更新方式 |
|---|---|---|---|
| **规则**（R*） | `when/transform/verify/evidence` | 移植实录、fork 变更、踩坑记录 | 人工评审后合入 |
| **错误指纹**（E*） | `fingerprint(归一化) → cause → fix(rule/patch) → 命中次数` | 每次迁移的失败日志 | **自动回灌**（见 5.5），命中率驱动排序 |
| **样本**（S*） | 仓库 + commit + 平台 + 验证结论 | 4 个真实迁移 + 公开样本 | 每完成一次迁移追加 |

蒸馏流程（把已有 270KB 文档变资产）：

```text
docs/*.md（移植实录/踩坑记录/PORTING_GUIDE/可优化事项）
   -> LLM 抽取"现象-根因-修复-验证"四元组（结构化输出，人工抽检）
   -> 去重合并 -> 生成 E*/R* 候选
   -> 在样本仓库上回放验证（规则必须至少在一个真实样本上生效）
   -> 合入 KB 并标注 evidence（commit/文章锚点）
```

**关键约束**：未在真实样本上回放通过的规则**不进主线**（防止"看起来对"的规则污染）。这条对评审很重要——它说明规则库不是 prompt 堆出来的。

## 9. 评测方案与实验设计（评审最看重的部分）

### 9.1 数据集

- **真实样本（自建，6~10 个）**：`habit-tree`、`tauri-mqtt-client-ohos`、`m3u8dl-tauri`、`cc-switch-harmonyos`、`juCang`、`mark_note` 等本地真实项目（覆盖：本地存储型、网络/长连接型、媒体处理型、纯前端型）；
- **公开样本**：Tauri 官方 examples、`tauri-demo`、社区常见模板（覆盖最小项目到中型项目）；
- **负样本**：含平台重度耦合（串口/系统托盘/原生菜单）的项目，用于验证"评分能识别不可自动化项"。

### 9.2 指标（可量化、可复现）

| 指标 | 定义 | 目标（初定） |
|---|---|---|
| **TTHW**（Time To Hello-World HAP） | 从干净仓库到"真机安装并启动无 panic"的墙钟时间 | 样本中位数 ≤ 15 min（含首次工具链安装另计） |
| **AFAR** 自动修复率 | Agent/规则自动闭环解决的错误指纹 / 总错误指纹 | ≥ 70% |
| **HIR** 人工干预次数 | 需要人决策的 Assist/Guide 动作数 | ≤ 3 次/项目 |
| **RPR** 真机回归通过率 | 功能清单通过项 / 总数 | ≥ 90% |
| **DNI** 桌面不回归 | 三平台构建 + 桌面冒烟是否通过 | 100% |
| **规则命中率** | 规则解决占比 vs LLM 解决占比 | 规则 ≥ 60%（证明"确定性优先"有效） |
| **成本** | 每次迁移 token 数与耗时 | 记录并优化 |

### 9.3 基线与消融（把"AI 有用"变成结论而不是主张）

| 组 | 配置 | 预期结论 |
|---|---|---|
| B0 | 纯人工照文档（作者自己前两次的实录耗时） | 基线，最慢 |
| B1 | 纯规则脚本（现有 `port-to-ohos.ps1` + 文档） | 能构建，但前端兼容/平台 API 全卡人工 |
| B2 | 纯 LLM 无验证（一把梭改全仓库） | **对照组**：预期高失败率/幻觉改动/无法自证 |
| B3 | 本项目 | 全指标领先，且证据完整 |
| A1 | B3 − Verifier | 证明"证据闸门"的贡献 |
| A2 | B3 − KB（无指纹库） | 证明"知识沉淀"的贡献 |
| A3 | B3 − Shims | 证明"兼容层"的贡献 |

**建议论文/答辩图**：① 各方法 TTHW 箱线图；② 错误指纹自愈漏斗（发现→命中→修复→复验通过）；③ 消融柱状图；④ 一次完整迁移的证据链时间线。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 幻觉乱改代码 | 引入难以定位的回归 | 六道闸（5.5）；结构化补丁；桌面回归闸；轮次上限 |

| 评测被质疑"自证" | 分数不可信 | 全部指标脚本化、原始日志入库、消融实验公开；证据链可一键复现 |

## 13. 创新点小结（答辩口径）

1. **证据驱动的迁移闭环**：把"迁移成功"定义为**四层可观测证据**（静态/构建/产物/运行时）全部闭合，而非"编译过了"。其中 `.so 内嵌 AssetKey 指纹`、`HAP 死资源检测`、`版本号反推前端是否进 .so` 等探针来自真实血泪教训，具备**不可抄的细节深度**。
2. **规则优先、AI 兜底的分层架构**：可枚举的机械改造零 token、零不确定性；LLM 只处理规则未命中的长尾，且必须产出结构化补丁并通过六道安全闸。**用指标（规则命中率 ≥ 60%）自我约束**，反"AI 万能"叙事。
3. **前端 ArkWeb 兼容层作为一等交付物**：把"每个应用各自踩一遍 localStorage/confirm/color 的坑"变成"一次实现、全局复用、业务零改动、桌面不回归"。
4. **知识库由真实迁移记录蒸馏而来**：4 个已完成迁移 + 约 270KB 实录构成语料，规则/指纹均带 commit 级证据链，且必须**在样本上回放通过**才进主线。
5. **先诊断后动手**：可迁移度评分 + 阻塞项分级把人从"改到哪算哪"变成"先知道要花多少人力、哪些不可自动化"。
6. **面向鸿蒙 PC（2in1）而非手机**：设备类型、多窗口、键鼠、DPI、上架自查均显式建模，能力矩阵由工具**自测**而非抄文档。
