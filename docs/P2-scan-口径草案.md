## 一、三个必须先回答的问题

| # | 问题 | 为什么它决定扫描器怎么写 |
|---|---|---|
| Q1 | **"一项"是什么？** | 决定扫描器的遍历粒度、输出行数、报告怎么看 |
| Q2 | **覆盖率的分子分母怎么算？** | 决定验收能不能被复核，以及"识别不全"怎么暴露 |
| Q3 | **"有结论"包括哪些取值？** | 决定"人工待定"算不算数——这直接决定验收能不能被糊弄 |

## 二、Q1 我的建议：以「迁移单元」为一项

**定义**：一项 = **需要做出一次处置决定的最小对象**。不是文件、不是行、不是出现次数。

理由：迁移的产出是"决策"，不是"改动行数"。同一件事出现 20 次也只需决定一次（然后批量应用）。

### 五类清单的"项"定义

| 类 | 一项 = | 附带记录 | 归并规则 |
|---|---|---|---|
| **命令** | 一个 `#[tauri::command]` **函数** | `sites[]`（调用点文件:行）、是否进 `generate_handler!` | 同名重载按函数合并 |
| **事件** | 一个**事件名** | 发送端 `sites[]` / 监听端 `sites[]`、载荷字段 | Rust 侧与前端侧同名合并 |
| **插件** | 一个**插件**（`tauri-plugin-*` 或前端 `@tauri-apps/plugin-*`） | 版本、启用 features、被哪些命令用到 | 两侧同一插件合并为一项 |
| **前端能力** | 一个**浏览器能力**（见下） | 使用点 `sites[]` | 不按文件数算 |
| **平台 API** | 一个**API 符号**（如 `rfd::FileDialog`、`app_data_dir`、`Command::new`） | 调用点 `sites[]`、所在 cfg 条件 | 同一符号跨文件合并 |
| **依赖 crate**（P3 消费） | 一个 **crate** | 版本、来源（crates.io/git）、依赖链 | 按 `cargo metadata` 的包 id |

**关键改动（相对"扫文件"的直觉）**：前端资源**不按文件数**算，而是按**浏览器能力**算。理由：
`dist/assets/` 里 31 个 js 文件对处置没有意义，真正要决策的是
`localStorage` / `confirm` / `prompt` / `Blob` 下载 / `<input type=file>` / `<input type=color>` /
`Notification` / `fetch` 跨域 / `clipboard` 这些**能力**（每个能力在 ArkWeb 上的处置结论不同）。

> 如果你更想要"文件/行"口径（便于跟代码审查对齐），那就变成 **C1'（文件级覆盖）**，
> 但我不建议用它当验收口径——它衡量的是"我看过哪些文件"，不是"我决定了哪些事"。

## 三、Q2 覆盖率的算法：三个指标，别只报一个

```
识别项  R = Σ(五类清单各自的项数) + 依赖 crate 数
有结论项 D = R 中处置结论 ∈ {改造, 降级, 不适用, 人工} 的项数
人工项  H = 处置结论 = 人工 的项数
未知项  U = 处置结论 = 未知/解析失败 的项数      （必须为 0）

C1 结论覆盖率 = D / R          ← 验收 A2 的「100%」指这个
C2 发现置信度 = 1 − 漏识别数 / 人工基线项数      ← 防止"我只识别了我认识的"
C3 人工占比   = H / R          ← 与验收 A3（人工介入 ≤5 处）挂钩
```

**为什么要 C2**：C1 有个天生漏洞——"我识别的每一项都有结论"很容易达成，只要识别得少。
所以必须再加一条**反向校验**：在 ≥1 个样本上人工列一份基线清单（推荐 `habit-tree`，
它的 `docs/鸿蒙移植改动说明.md` 里有现成的 10 改 + 59 增可作 ground truth），
与扫描结果做双向 diff：

- **漏识别**（人工有、扫描没有）→ 必须补规则，C2 直接掉分；
- **多识别**（扫描有、人工没有）→ 允许，但要逐条解释（通常是"识别到了但本次判定不需要改"）。

**C1 与 C3 必须成对使用**：只报 C1=100% 没意义（把一切都标"人工"就 100% 了）；
配上 C3（人工占比）和 A3（人工介入绝对数 ≤5）才关得住。

## 四、Q3 处置结论的取值域（四值 + 一禁用值）

| 取值 | 含义 | 是否计人工 | 谁产生 |
|---|---|---|---|
| `改造` | 规则能直接改（fork pin、cfg 分支、shim 注入…） | 否（自动） | 规则引擎 |
| `降级` | 能力位为 0，走替代实现（托盘→最小化、原生对话框→应用内） | 否（若规则覆盖）；是（若需人确认接口形态） | 规则 + 审批 |
| `不适用` | OHOS 上不存在该概念（`explorer.exe`、`Command::new("start")`） | 否 | 规则 |
| `人工` | 需要人判断（选择降级形态、业务语义权衡） | **是**，逐条计入 A3 | Agent/扫描器标出，人来定 |
| `未知` | 解析失败 / 无法归类 | **禁用**：出现即 C1 < 100%，门禁不放行 | — |

**"人工"算不算"有结论"？我的建议：算**（否则一个需要人决策的东西会让覆盖率永远差几项），
但**必须同时满足两条**：
1. 每条 `人工` 都要带 `question`（一句话说清"人要定什么"）与 `candidates[]`（可选方案）；
2. `人工` 的**绝对条数**进 A3 统计，≤5 处。

## 五、可迁移度评分口径（必须可解释）

五维，各自 0–100，总分加权：

| 维度 | 权重 | 扣分规则（可复现） |
|---|---|---|
| 构建链 | 0.20 | `hard` 阻塞 −20/项（封底 0）；`soft` −5/项 |
| 依赖 | 0.25 | 不可用 crate −15/项；需 patch −5/项 |
| 运行时 | 0.25 | ArkWeb 缺能力/缺 API −15/项；渲染已知缺陷 −10/项 |
| 平台 API | 0.20 | 硬阻塞 API −15/项；可降级 −5/项 |
| 分发 | 0.10 | 需人工签名/上架材料 −10/项 |

**硬约束**：每个扣分项必须能指回一个 `blocker.id`；评分页点开能看到"为什么扣这 15 分"。
**分数不是营销**：它唯一的用途是排序"先迁哪个应用、预计还要多少人时"（`工时 ≈ Σ eta`）。

## 七、验收自检（怎么证明 100% 不是自说自话）

在 `habit-tree` 上跑一遍，产出三件东西：

1. `scan.json`（上面的 schema）；
2. `coverage.json`：`R/D/H/U` 与五类分布，逐类可展开；
3. **基线 diff 表**：以 `habit-tree/docs/鸿蒙移植改动说明.md` 的「10 改 + 59 增」为人工基线，
   列出 `漏识别` 与 `多识别`，每条给结论（补规则 / 解释）。

出口判据（写进路线图 P2）：
- `C1 = 100%`（`U = 0`）；
- `漏识别 = 0`（C2 只在"多识别"上有扣减）；
- 每条 `verdict` 都能指到 `rule` 或 `evidence`；
- `H`（人工项）与 A3 的 ≤5 口径一致。

## 八、需要你拍板的三件事（其余按草案执行）

| # | 选择题 | 我的建议 | 影响 |
|---|---|---|---|
| **1** | "一项"用**迁移单元**（函数/事件名/插件/能力/API 符号/crate）还是**符号出现次数**？ | **迁移单元** | 影响 R 的数值与报告可读性；出现次数会让 R 虚高且无法处置 |
| **2** | `人工` 算不算"有结论"？ | **算**，但要带 `question`+`candidates`，且绝对条数进 A3 | 算 → 覆盖率可达 100%；不算 → 覆盖率永远 ≤ 95% 且与 A3 冲突 |
| **3** | 前端那一类按**浏览器能力**算，还是按**文件数**算？ | **浏览器能力** | 按文件数对处置无意义；按能力才能一条一条给替代方案 |

拍板后我把这三条写进 `docs/实施路线图.md` P2 的出口判据，然后开始写扫描器。
