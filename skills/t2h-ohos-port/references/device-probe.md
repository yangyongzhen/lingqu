# 真机功能自测（点了有没有反应，让证据说话）

> 什么时候读：要在真机上证明"某个功能到底能不能用"时（`verify` 的 `platform-api` 已过、
> 但界面上的功能还没实测；或用户问"这个按钮点了有反应吗"）。
> 一条命令的用法在 `SKILL.md`；本文是闭环与判定口径。

## 0. 边界：什么不算"可用"

「进程在跑 / 日志正常 / 截图看着像」都不算功能可用。要判定某个功能，必须在真机上
**点它一下，再对比点了之后发生了什么**——这一步是 agent 自己能做、也应当自己做的实验。

## 1. 闭环六步（`lingqu-cli probe` 已把它做成一条命令）

1. `dumpLayout` 存 before
2. 按**文本**找节点，取 `attributes.bounds` 的 `"[x1,y1][x2,y2]"` 中心——
   **别按截图估坐标**：设备 1840×2800，截图是缩放过的，估出来的点必偏（实测两次都点歪）
3. `uiInput click <x> <y>`
4. 再 dump 一次 after，比对文本集合：**冒出新的实质文本 = 有反应；一字不差 = 没反应**
5. 截图归档（给人看，也是第二路证据）
6. 结论写进 `.lingqu/verify/<工程>.probe.json`，`verify` 会**优先**采用它（实测压过静态推断）

```bash
lingqu-cli probe --path . --feature pick_m3u8_file --click-file ./pick.txt
lingqu-cli probe --path . --feature start_download --click-file ./start.txt --expect-log-file ./expect.txt
```

## 2. 判定口径

| 现场 | 结论 | 理由 |
|---|---|---|
| 点后版面**多出新文本**（且不含"无法/失败/错误"） | `pass` | 有反应 |
| 日志命中 `--expect-log` | `pass` | 有反应的另一种证据 |
| 版面**一字不差** | **`unknown`** | 分不清"没点中"与"真无响应"——**不许直接判 fail**（判 fail 是拿观测缺陷冒充功能缺陷） |
| 只有纯数字/半角标点在变（时钟 `09` / `:` / `48`、字数 `0`、编辑器里的 `, ? !`） | **不算变化** | 这些是页面自己会动的噪声，据此判 pass 是**假绿** |

落档里有 `verdict / note / evidence`，`note` 要写清"多出了哪条文本"或"节点数 35→35"，别只写"失败"。

## 3. 纪律

- **中文一律写进 UTF-8 文件再传**（`--click-file` / `--expect-log-file`）：仓颉在 Windows 上接不到
  非 ASCII 的 argv，`--click 选择文件` 会直接崩（AGENTS §4-119）。
- 探针**不计人工介入**（A3）——这是 agent 自己做的实验。
- 判不准就如实记「未测」，别凑结论。需要前置现场的（例：取消下载要先有"下载进行中"）、
  需要滚动或跨窗口才看得见的节点，都属于这一类。
- **每轮重取候选**：点一下版面就换一层，别拿第一份 dump 枚举出的清单一路点到底
  （实测第一版只拿到 1 条 pass、其余全"找不到节点"）。
- 真机验桥/验功能优先选**有文本的入口**：ArkWeb 内纯图标控件在 `dumpLayout` 里**不映射成独立节点**，
  只能靠截图比例估坐标——那种点按十个有九个不中。
- 点击命令返回 `No Error` **只表示命令送出去了**，不表示点中了：判定看应用 hilog + 前台 bundle + 截图三路旁证。
